# 피드백 정리

사용자가 작업 중에 준 지적·선호·교정을 다음 작업에서도 쓰이게 옮긴다. 입력은 대화 기록 파일이다.
에이전트가 "피드백을 받으면 적어 둔다"에 기대지 않는다. 압축은 모델 컨텍스트만 줄이고 `.jsonl` 에는 사용자
메시지가 전부 남는다.

반영은 사용자가 고른 것만 한다. 목록 승인은 반영 승인일 뿐 submit·커밋 승인이 아니다.

## 1. 뽑기

원본 대화 기록, 추출 출력, 처리 로그, 후보 목록은 공개 플러그인 체크아웃에 만들거나 복사하지 않는다.
`<scratchpad>`와 `HAN_DISTILL_LOG`가 저장소 밖의 비공개 위치인지 확인한다. 회사·고객·비공개 프로젝트의
기록을 처리할 때는 해당 자료를 둘 권한이 있는 위치만 쓴다.

```
python "${CLAUDE_PLUGIN_ROOT}/skills/distill/scripts/distill.py" extract --out <scratchpad>/distill.md
```

- Bash 도구로 돌린다. 훅이 내보낸 환경변수는 `CLAUDE_ENV_FILE` 을 읽는 Bash 도구에만 들어가고 PowerShell 에는 없다.
- 일반 세션은 `--transcript` 없이 돌린다. SessionStart 훅이 `HAN_TRANSCRIPT`(지금 세션의 대화 기록)를 내보낸다.
  비어 있으면 세션 시작 뒤 훅이 안 돈 것이니 사용자에게 대화 기록 경로를 묻는다. `ls -t` 로 최신 파일을 고르지 않는다
  (세션을 동시에 여러 개 띄우면 남의 기록을 집는다).
- 미션은 `mission_state.py transcripts` 가 준 경로마다 `--transcript` 를 붙인다.
- 이미 정리한 메시지는 로그의 워터마크로 건너뛴다. 처음부터 다시 보려면 `--all`.
- 출력 파일을 Read 로 읽는다. 콘솔은 CP949 라 한글이 깨지니 stdout 으로 본문을 보지 않는다.

## 2. 고르기

메시지마다 `앞 답` 을 같이 읽고, 다음 작업에서도 행동을 바꿀 말인지 본다.

- 남길 것: 접근·설계 교정("이건 서버가 해야지"), 코드 스타일 지적, 작업 방식 교정("묻지 말고 해", "리뷰 결과 먼저
  보여 줘"), 반복된 불만.
- 버릴 것: 이번 작업만의 지시·선택, 승인·진행 신호, 단순 질문, 이미 이번 작업에서 반영돼 끝난 일회성 수정.

대부분 버린다. 남길 게 없으면 "남길 것 없음"이라고 말하고 `record --verdict 확인` 으로 워터마크만 올린다.

## 3. 반영할 곳 정하기

회사·고객·비공개 프로젝트의 지침·요구사항·사례는 `rules`·`plugin` 후보로 올리지 않는다.
원문 복사뿐 아니라 요약·익명화한 내용을 공개 플러그인에 반영하는 것도 금지한다.
이 항목은 해당 자료를 둘 권한이 있는 비공개 프로젝트의 `guide` 또는 저장소 밖의 개인 로컬 설정·메모리로만
분류한다. 허용된 위치를 확정할 수 없으면 반영을 보류하고 묻는다. 공개용 일반 규칙으로 바꿔 우회하지 않는다.

| dest | 대상 | 고르는 기준 |
| --- | --- | --- |
| `guide` | 프로젝트 가이드·규칙 문서 | 팀 누구에게나 적용될 코드·네이밍·설계 규칙. 프로젝트 문서 규칙대로 쓴다 |
| `memory` | 자동 메모리 | 이 사용자의 작업 습관·선호, 프로젝트 문서에 둘 성격이 아닌 사실 |
| `rules` | han 개인 규칙 | 프로젝트를 가리지 않는 사용자의 작업 원칙 |
| `plugin` | han 플러그인(CLI·가드·스킬) | 미션·슬롯 절차 자체의 실수 |

코드 규칙은 메모리가 아니라 `guide` 가 기본이다. 프로젝트에 가이드 문서가 없으면 `memory` 로 낮추고 이유를 적는다.

각 후보마다 막는 수단을 위에서부터 따진다: 구조(실수가 나올 길 없애기) → 타입·스크립트·가드 → 테스트 → 문서·규칙.
문서 한 줄은 기계로 못 막는 것만이다. 고른 단계와 더 높은 단계가 안 되는 이유를 후보에 적는다.

## 4. 겹침 확인

제안하기 전에 대상마다 검색한다.

- `guide`: 프로젝트 문서(CLAUDE.md 가 가리키는 규칙·가이드 폴더)
- `memory`: memory 폴더와 `MEMORY.md`
- `rules`·`plugin`: han 원본 저장소(아래 "han 원본 위치")
- 지난 판정: 로그 TSV(`HAN_DISTILL_LOG`, 기본 `~/.claude/han/distill/log.tsv`)의 `기각` 줄. 같은 내용이면 다시 올리지 않는다.

이미 같은 규칙이 있는데 이번에 또 어겼으면 문장을 더 쓰지 않는다. "있는데 안 지켜짐"으로 표시하고 가드·테스트
후보로 올린다.

## 5. 보여 주기

번호 목록으로 보여 준다. 일반 세션은 채팅에, 미션은 `confirm-C.md` 의 `## 피드백 반영 후보` 절에 싣는다.

항목마다:
- 원문 인용(짧게)과 그 말이 나온 맥락 한 줄
- dest 와 대상 파일
- 바꿀 문장 초안 또는 바꿀 코드 요지
- 고른 단계(구조·가드·테스트·문서)와 이유
- 겹침 확인 결과(새 항목 / 있는데 안 지켜짐)

`rules` 후보가 있으면 Codex 사본도 같이 고칠지 따로 묻는다.

## 6. 반영과 기록

- 사용자가 고른 번호만 반영한다. 나머지는 기각이다.
- `guide`: 프로젝트의 파일 변경·문서 규칙대로. 버전 관리가 있으면 작업 단위(CL·브랜치)에 담고 제출은 하지 않는다.
  미션 중이면 그 미션의 작업 단위에 같이 담는다.
- `memory`: 기존 파일이 있으면 고치고, 새로 만들면 `MEMORY.md` 에 한 줄 색인을 단다.
- `rules`: 주입 상한이 `CONTEXT_LIMIT`(`hooks/session_rules.py`, 10000자)다. 고친 뒤 8000자를 넘으면 추가 대신
  기존 문장 정리를 먼저 제안한다.
- `rules`·`plugin` 을 고쳤으면 버전을 올리고 플러그인을 갱신해야 새 세션에 들어간다고 사용자에게 알린다. 커밋은
  사용자가 요청할 때만.
- 항목마다 로그에 남긴다. `--until` 은 extract 가 출력한 그 세션의 `until` 값이다.

```
python "${CLAUDE_PLUGIN_ROOT}/skills/distill/scripts/distill.py" record --session <id> --until <ts> --verdict 반영 --dest guide --summary "<한 줄>"
python "${CLAUDE_PLUGIN_ROOT}/skills/distill/scripts/distill.py" record --session <id> --until <ts> --verdict 기각 --summary "<한 줄>"
```

남길 것이 없었거나 모두 처리했으면 `--verdict 확인` 한 줄로 워터마크를 올린다.

## han 원본 위치

기준 저장소는 `https://github.com/notdevblue/han-orchestrator`다. `rules`·`plugin`은 이 저장소의 개발 체크아웃을 고친다.
`${CLAUDE_PLUGIN_ROOT}`의 플러그인 캐시와 `known_marketplaces.json`의 `installLocation`에 있는 마켓플레이스
clone은 설치·갱신용 사본이며 개발 원본으로 쓰지 않는다.
기존 개발 체크아웃의 Git remote가 기준 저장소를 가리키는지 확인한다. 디렉터리 구조나 manifest가 있다는 이유로
원본으로 판단하지 않는다. 개발 체크아웃의 경로를 확정할 수 없으면 사용자에게 묻는다.

- Claude 개인 규칙: `plugins/han/rules/personal-rules.md`(서브에이전트에도 주입), `plugins/han/rules/main-session.md`(답변·계획·서브에이전트 파견처럼 메인 세션에만 주입)
- Codex 개인 규칙: `plugins/han/codex/rules/` 아래 같은 두 파일(서브에이전트 파견 내용이 Claude 쪽과 다르다)
