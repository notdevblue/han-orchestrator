# 슬롯 워크스페이스

슬롯은 같은 스트림·브랜치를 받는 별도 워크스페이스다. 슬롯 폴더에서 띄운 Claude 세션 하나가 미션 하나를
맡는다. 세션마다 MCP 연결·에디터·`ACTIVE`가 따로라 미션끼리 서로 막지 않는다.

설정은 어댑터의 `slots`(계약은 `../mission/references/adapter-schema.md`의 "슬롯"), 프로젝트별 준비 단계와
실측 시간은 `adapter.md`의 "슬롯 준비"에 있다.

## 규칙

- **스크립트만 쓴다.** 작업 공간 만들기·동기화·폴더 복사·링크·삭제를 손으로(p4, robocopy, rm 등) 치지 않는다.
  스크립트가 슬롯인지 확인, 잠금, 상태 기록까지 한꺼번에 하므로 손으로 하면 그 보호가 빠진다.
- 실패하면 출력에 적힌 로그 경로(`<stateDir>/slots/<이름>-<단계>.out.log`)와 요약을 사용자에게 보고하고 멈춘다.
  스스로 고치려고 같은 명령을 반복하거나 다른 명령으로 우회하지 않는다.
- `create`·`refresh`·`remove`·`run`은 **미션이 열려 있지 않은 세션에서만** 돌린다. 미션 중이면 가드가 막는다.
  `status`는 읽기 전용이라 언제든 된다.
- 슬롯 이름은 어댑터 `slots.names`에 있는 것만 받는다(영숫자로 시작, 영숫자·`_`·`-`).
- 미션 시작·재개에는 에디터를 열지 않는다. `--editor`는 사용자가 함께 열어 달라고 명시했을 때만 붙인다.
  검증·에셋 임포트에 필요해지면 미션 세션에서 `adapter.md`의 에디터 수명 절차로 열고, 이번 작업에서 연 것만 끝나면 정상 종료한다.

## 호출

```
python "${CLAUDE_PLUGIN_ROOT}/skills/slots/scripts/slots.py" <명령> [인자] [--project <메인 프로젝트 폴더>]
```

- 어댑터는 현재 폴더에서 위로 찾고, 없으면 레지스트리(`HAN_ADAPTERS_DIR` 환경변수가 가리키는 폴더의
  `projects.json`)의 `roots`로 찾는다. 다른 폴더에서 부르면 `--project`로 메인 프로젝트 폴더를 준다.
- "어댑터를 찾지 못함"으로 끝나면 `HAN_ADAPTERS_DIR`가 이 세션 환경에 없다는 뜻이다. 사용자에게 알린다.
- 종료 코드 0 성공, 1 실패(요약의 `failed`), 2 사용 오류(인자·설정).
- 슬롯 목록·상태는 메인 프로젝트의 `<stateDir>/slots.tsv`에 쌓이고, 직접 고치지 않는다.

```
name	path	client	created	synced	state
```

`state`는 `creating`(만드는 중이거나 중단됨), `ready`, `failed:<단계>`(만들다 실패), `failed:refresh:<단계>`(갱신하다 실패)다.
`ready`가 아니면 `run`은 거부한다.

## 명령

- `status [이름...]` — 슬롯별 폴더·작업 공간 존재, 열린 파일 수, `ACTIVE`(돌고 있는 미션)와 그 상태·단계,
  마지막 동기화, `state`, 비고를 표로 보인다. 어긋난 것은 표시만 하고 고치지 않는다. 슬롯 폴더에서 현재
  작업 공간 이름이 슬롯 것이 아니면 비고에 경고가 붙는다(환경변수·레지스트리 `P4CLIENT`가 설정 파일을 이기는 경우).
- `create [이름...] [--jobs N] [--dry-run]` — 슬롯을 새로 만든다. 이름이 없으면 폴더가 없는 `slots.names` 전부.
  폴더나 작업 공간이 이미 있으면 건드리지 않고 `skipped`로 알린다. 순서는 `adapter.md`의 "슬롯 준비"이고
  `기준 CL: <번호>`가 먼저 출력된다. 같은 이름을 여러 번 줘도 한 번만 만든다. `--jobs`는 동시에 만들 슬롯 수(기본 2).
  끝나면 `state`가 `ready`, 실패하면 `failed:<단계>`가 된다. 성공한 뒤 레지스트리 `roots`에 슬롯 폴더가 없으면 경고한다.
- `create <이름...> --resume [--dry-run]` — 중간에 끝난 슬롯을 이어받는다. 폴더와 작업 공간이 있고 이 도구가 만든
  슬롯으로 확인되며 `ready`가 아닌 슬롯에 대해, 작업 공간·폴더 만들기는 건너뛰고 준비 단계 전체를 다시 돌린다.
  `slots.tsv`에 행이 없는 슬롯도 대상이다. 이름이 필요하다. `--dry-run`은 대상 여부와 돌릴 단계만 보인다.
- `refresh <이름...> [--keep-local | --discard-local] [--main-keep-local] [--dry-run]` — 기준 CL로 다시 동기화하고
  `slots.refresh` 단계(보통 동기화·임포트)를 돌린다. 슬롯에 `ACTIVE` 미션이 있으면 거부한다. 열린 파일이 있으면 목록을 보이고
  거부하며 `--keep-local`로 진행한다. 열리지 않은 채 바뀐 파일(동기화가 덮어쓸 것)이 있어도 목록을 보이고
  거부하며 `--discard-local`(버림)이나 `--keep-local`(보관)로 진행한다. 두 옵션은 같이 못 쓴다.
  `slots.churn`(엔진이 스스로 다시 쓰는 추적 파일)은 로컬 변경 검사에서 빠지고, 검사를 통과하면 단계 실행 전에
  `p4 sync -f <파일>#have`로 depot 내용으로 되돌린다. 그 파일이 열려 있으면 작업물이라 거부한다.
  `--keep-local`은 열리지 않은 채 바뀐 파일(churn 제외)을 `han slot keep-local <이름>` 설명의 보관 pending CL(없으면 만들고
  있으면 재사용)에 `reconcile -e -c`로 열고, `slots.refresh`의 `sync` 단계가 끝난 직후 `resolve -am`을 한 뒤
  `resolve -n`으로 남은 충돌을 본다. 충돌이 남으면 멈추고 `failed:refresh:resolve`로 두며 충돌 파일을 보인다(직접 resolve한 뒤
  `refresh --keep-local` 다시). 열린 파일은 그대로 두고 보관 CL 번호와 연 파일 수를 출력한다. 이 옵션은 `slots.refresh`에
  `sync` 단계가 있어야 한다. 갱신이 끝나면 `ready`, 실패하면 `failed:refresh:<단계>`이고 다시 `refresh`로 복구한다.
  슬롯을 만지기 전에 **메인 워크스페이스(`slots.mainClient`)를 head로 먼저 sync**한다(명령 하나에 한 번, `<stateDir>/slots/main.lock`).
  head CL을 `p4 changes -m1 //<stream>/...`로 하나 정해 그 번호로 받으므로 `{baseline}`이 head가 된다. 메인이 이미 최신이면 sync는 생략하고,
  대상 슬롯이 전부 거부 상태면 메인도 받지 않는다. 메인은 `clobber`라 열지 않고 고친 파일을 sync가 말없이 덮으므로, 그런 파일(
  `slots.churn` 제외)이 sync 대상에 있으면 목록을 보이고 거부하며 **메인 sync도 슬롯 갱신도 하지 않는다**. 이때는 목록을 사용자에게 보여 주고
  어떻게 처리할지 물은 뒤에만 `--main-keep-local`을 붙인다(메인의 `han main keep-local` 보관 pending CL에 `reconcile -e -c`로 열고 진행). sync 뒤
  `resolve -am`·`resolve -n`으로 충돌이 남으면 목록을 보이고 멈추며 슬롯은 갱신하지 않는다. 성공하면 `메인 sync: <이전 have> → <head> (파일 N개)`가 출력된다.
  `create`는 메인을 받지 않고 메인의 현재 have를 기준으로 한다.
  `--discard-local`은 진짜 작업물을 버려도 될 때만 쓴다. auto mode 권한 검사가 이 옵션을 막으면 사용자가 `!`로 직접 실행하게 안내한다.
- `run <이름> <작업...> [--refresh] [--editor] [--keep-local | --discard-local] [--main-keep-local] [--dry-run]` — 슬롯 폴더에서
  Windows Terminal 새 탭을 띄워 `claude "/han:mission <작업>"`을 시작한다. 슬롯이 `ready`이고 `ACTIVE`가 없어야
  한다(`--resume`은 반대). `--refresh`는 먼저 `refresh`를 하고(메인 선행 sync와 `--keep-local`·`--discard-local`·`--main-keep-local`이 그쪽에 적용된다; `--main-keep-local`은 `--refresh` 없이 못 쓴다), `--editor`는
  `slots.editor` 명령으로 그 슬롯의 엔진 에디터를 함께 연다. 작업 문자열에는 큰따옴표와 개행을 쓸 수 없다.
- `run <이름> --resume [--new-session] [--editor] [--dry-run]` — 진행 중 미션을 새 탭에서 이어서 연다. 슬롯 폴더에서 Windows Terminal
  새 탭으로 `claude "/han:mission 미션 이어서"`를 띄운다. 슬롯이 `ready`이고 `ACTIVE`가 **있어야** 한다(일반 `run`과 반대).
  작업 문자열을 받지 않고, `--refresh`·`--keep-local`·`--discard-local`·`--main-keep-local`과 같이 쓰지 못한다(진행 중 미션의 열린 파일을
  동기화로 건드리면 안 되기 때문). `--editor`는 일반 `run`과 같다.
  `ACTIVE.session`이 다른 런타임(Codex) 세션이거나 기록을 못 찾으면 거부한다. 사용자가 이 런타임으로 넘겨받겠다고 하면
  `--new-session`을 붙여 기존 세션을 열지 않고 새 세션에서 `미션 이어서`를 시작한다(새 세션의 미션 절차가 다른 창에서 아직 도는지 확인받음).
- `remove <이름...> --yes [--discard-local]` — 작업 공간과 폴더를 지우고 `slots.tsv`에서 뺀다. 되돌릴 수 없으니
  **사용자에게 그 자리에서 확인받은 뒤에만 `--yes`**를 붙인다. `ACTIVE`·열린 파일·shelve·pending CL이 있으면
  목록을 보이고 거부한다. 기록되지 않은 로컬 변경(새 파일·편집·삭제)이 있어도 목록을 보이고 거부하며, 사용자가
  버려도 된다고 한 뒤에만 `--discard-local`을 붙인다. `creating` 슬롯은 지우지 않는다(먼저 `create --resume`).
- 모든 명령의 `--dry-run`은 실행할 명령과 거부 사유만 출력한다(읽기 전용 VCS 조회만 한다).

## 흐름

새 슬롯: `status` → `create <이름> --dry-run`으로 기준 CL과 단계를 확인 → `create <이름>`. 중간에 끊겼으면 `status`에서
`creating`·`failed:*`·`slots.tsv 에 없음`을 보고 `create <이름> --resume`.

미션 돌리기: `status`로 `ready`이고 `ACTIVE`가 없는 슬롯을 고른 뒤 `run <이름> "<작업>" --refresh`.
여러 슬롯의 미션이 같은 파일을 건드리지 않게, 각 미션의 계획 단계는 다른 작업 공간에서 열린 파일
(`adapter.md`의 확인 명령)을 피해 배분한다. 확인 A·B·C는 슬롯 세션마다 받고, submit은 그 슬롯 세션에서 슬롯 작업 공간의
작업 단위로 한다. 다른 슬롯과 같은 파일을 바꿨으면 먼저 submit된 쪽이 이기고, 뒤 슬롯은 동기화·병합이 필요하다(사용자 확인 대상).
진행 중 미션을 새 탭에서 다시 열 때는 `run <이름> --resume`(wt.exe 를 손으로 부르지 않는다 — 부모 세션
환경변수가 넘어가 대화 기록이 안 남음).

지우기: 사용자 확인 → `remove <이름> --yes`. 폴더를 에디터·터미널이 잡고 있으면 삭제가 실패하고 `state`가
`failed:remove`가 되니, 닫고 같은 명령을 다시 한다.

## 미션 대시보드

메인·슬롯 전부의 미션 상태(진행·중단·닫힘, 답 기다리는 질문, 마일스톤 진행, 마지막 활동)를 한 화면에 보는
읽기 전용 로컬 서버다. 공유된 ask·confirm·보고와 답 이력을 열람한다. 답과 승인은 현재 미션 대화에서 받는다.
요청마다 디스크를 다시 읽고 `127.0.0.1`에만 바인드한다.

```
python "${CLAUDE_PLUGIN_ROOT}/skills/slots/scripts/dashboard.py" [--project <메인 프로젝트 폴더>] [--port 8765] [--open]
```

- 계속 떠 있는 프로세스라 **백그라운드로 실행**한다. `--open`은 브라우저를 함께 연다.
- 포트가 이미 쓰이면 한 줄 오류와 종료 코드 2로 끝난다(`--port`로 바꿈).
- `ACTIVE`가 없어도 `mission.md`가 있는 미션 폴더는 전부 보인다(`진행`인데 `ACTIVE` 없으면 "세션 없음" 표시).
- 슬롯은 데스크톱에서 2열 요약 카드로 모아 본다. 진행 미션에 답변이 필요한 슬롯을 먼저 표시하고, 각 그룹 안에서는 기존 슬롯 순서를 유지한다. 목표·지금 하는 일·다음·남은 일을 짧게 표시하고 전체 내용은 펼치거나 상세에서 확인한다. 진행 중 작업은 `units.tsv`의 모든 `doing`, 남은 작업은 `done`을 뺀 전체(진행 중 포함)다. 빈 슬롯은 아래에 작게 모은다.
- 목표는 `mission.md`의 `## 목표` 첫 줄에 작성한 짧은 요약을 한 줄로 표시한다. 범위·조건·상세는 그 아래에 보존하고 목표를 펼쳐 확인한다.
- 다음 후보에는 선행 작업 이름·상태와 사람 확인·금지 조건을 함께 표시한다. 선행 완료만으로 착수나 승인이 확정되지는 않는다. 의존 작업을 찾지 못하거나 자료를 읽지 못하면 미확인으로 표시하고, 마일스톤이 없으면 작업 계획 미등록으로 표시한다.
- 답변이 필요한 슬롯은 카드 상단에서 강조하고 질문 제목과 링크를 바로 표시한다. 문항 수·미답 수와 문서의 추가 승인 대기는
  `questions/<id>.json`의 `items[].status`·`approval.status`만으로 표시한다. 답 원문·권장안·대안의 문장으로 완료를 추정하지 않는다.
  문항이 모두 해결되고 문서의 추가 승인 대기가 없으면 미션 전체 확인 상태가 대기여도 `내 결정`에서 뺀다. 미션 전체 A·B·C 승인은 별도다.
  정본 누락·손상·생성본 직접 수정·등록과 표시 불일치는 미답·완료로 추정하지 않고 `기록 확인 필요`로 따로 표시한다.
  코디네이터가 `question check`로 확인하고 정본·생성본을 복구한다. 문서 링크와 열람 화면은 용도·제목을 먼저 표시하고 파일명은 보조 정보로 둔다.
- 업무 자료 갱신 시각과 세션 마지막 활동은 구분한다. 세션은 세션 없음 → 하위 작업 중 → 입력 기다림 → 작업 중(10분 안 활동) → 조용함으로 표시하며 대화 기록 끝부분으로 판정한다. 세션 활동은 업무 진행의 근거가 아니다.
- 상세 상단에는 현재·남은 작업 전체를 표시하고 완료 작업·원문·상태 표·세션 기록은 접어 둔다. 공유된 보고의 `## 지금`은 날짜를 붙인 최근 보고로만 표시한다. 중단·닫힘 미션은 당시 기록이다.
- 같은 슬롯의 다른 진행 미션도 링크로 표시한다. CLI 상태가 정본이며 대시보드는 디스크 상태를 읽는 요약 화면이다.
- 파일 링크(`/view`)는 메인·슬롯 루트 아래만 열고 밖은 403이다.
- 미션 루트의 `confirm-*.md`·`ask-*.md`와 대응하는 `details/<같은 파일명>.md`는 공유 등록 없이 자동 표시한다.
  `question publish`로 발행하고 `question answer`로 답을 기록한다. 생성 문서와 정본은 직접 고치지 않으며, 발행·답 기록 뒤와 공유 전에 `question check`를 실행한다.
  공유 해제 뒤에도 질문과 상세를 열 수 있다. 기존 Markdown 질문은 원문·답·승인 범위를 보존해 명시적으로 전환한다.
  자동 표시는 작성·독립 검토 완료나 승인을 뜻하지 않는다.
  `report.md`와 그 밖의 자료는 검토 후 `document share`에 각 경로를 명시 등록하고 `document list`로 확인한다.
  명시적으로 공유한 자료는 수정 뒤 재검토·재공유하며, 질문 이외의 링크·하위 파일은 자동 공유하지 않는다.
  `mission.md`·상태 TSV는 진행 상태로 계속 표시한다.
- 기존 문서의 사용자 입력과 답 이력은 보존한다. 답·승인은 현재 미션 대화에서 받고 코디네이터가 CLI로 기록한다. 대시보드가 답을 저장·전달하거나 중단된 세션을 자동 재개하지 않는다.
- 질문 정본·답 기록 계약은 미션 스킬의 `references/question-records.md`를 따른다. 실행 중인 이전 세션은 새 지침을 다시 읽는다.

## 알아 둘 것

- 같은 슬롯에 대한 `create`·`refresh`·`remove`는 동시에 못 돈다(`<stateDir>/slots/<이름>.lock`). 잠금이 사용 중이라는
  실패가 나오면 그 슬롯에서 다른 작업이 도는 중이다. 죽은 프로세스가 남긴 잠금은 알아서 정리된다. 임포트 같은
  `exclusive` 단계와 `slots.tsv` 쓰기도 프로세스 간 잠금을 쓰므로 여러 세션이 동시에 `create`해도 된다.
- 슬롯 세션은 `.claude/settings.local.json`(MCP 승인 등)과 개인 `_My/CLAUDE.md`, 프로젝트 자동 메모리(메인의 메모리 폴더를
  가리키는 junction)를 메인과 같게 받는다(`adapter.md`의 "슬롯 준비"). 새 폴더에서 처음 `claude`를 띄우면 폴더 신뢰
  확인 창이 한 번 뜨니 사용자가 승인해야 한다. 이 스킬은 전역 설정 파일을 건드리지 않는다.
- 기록 안 된 로컬 변경 확인(`reconcile -n`)은 슬롯 전체를 훑어 1분 넘게 걸릴 수 있다(`refresh`는 편집 확인만이라 더 짧다).
