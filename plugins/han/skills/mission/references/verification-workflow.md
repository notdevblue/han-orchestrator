# 검증과 완료 처리

코디네이터는 승인된 타깃 검증을 계획 파일로 만들고 `roles.verify` 하나에 상태 CLI의 `verify` 실행을 맡긴다.
Claude는 `han:verifier`의 Sonnet 5.5 / high, Codex는 `han_verifier`의 GPT-6 Luna / high로 고정한다.
등록되지 않은 Codex 역할은 `codex-roles.md`의 명시적 모델·추론 수준과 지시로 파견한다.
검증자는 코드·검증 범위·모델을 바꾸거나 하위 에이전트를 띄우지 않는다. 실패·예상 밖 상태는 증거와 미완료 이유를 반환한다.
검증 입력을 스냅샷으로 확정한 시점부터 결과 수집이 끝날 때까지 해당 입력을 바꾸는 작업을 동결한다.
공유 Unity는 코디네이터가 Refresh·컴파일·EditMode·Play 순서를 정하고, 관련 구현자와 그 하위 작업이 모두 반환하거나 정지되어 미완료임을 확인한 뒤 verifier 한 명만 실행한다. 검증 준비에서 필요한 `.meta` 생성·생성물 생성·CL 정리를 마친다.
Play 조작은 브리프의 순서·기대 결과·증거 경로를 따르며, 불명확하면 미확인으로 반환한다.
구현 에이전트가 만든 같은 형식의 결과도 실행기가 유효성을 확인한다. 검증 범위를 줄여 통과시키지 않는다.
미션 폴더의 `verification/`은 실행기 기록이며 사람이 덮어쓰지 않는다.

## 구현 단위 병렬화

`M1`을 시범 완료하고 승인된 계약을 고정한 뒤, `.cs`·`.meta`·생성물 파일 소유와 공유 파일·독점 자원 사용이 겹치지 않는 구현 단위는 병렬 파견할 수 있다. `ready`는 후보 목록일 뿐이므로 실제 충돌·승인·공유 자원 사용 가능성을 확인한다. `after`는 앞 단위의 `done`을 뜻하며, 파견이나 구현 반환만으로 충족되지 않는다. 병렬 구현을 검증하려고 공유 Unity를 동시에 쓰지 않는다.

브리프에는 기존 칸과 추가 주의사항을 써서 아래 항목 중 해당 작업에 필요한 것만 명시한다.

- **소유와 계약**: `.cs`·`.meta`·생성물 파일, CL, 공유 파일·독점 자원, 확정된 함수·RPC·상태 계약.
- **검증**: 타깃 명령·필터·조작·기대값과 관련된 실패·권한·미소유·경계값 반례.
- **사용자 기능**: UI·툴팁·locale·저장 중 이번 작업의 완료 범위.
- **반환**: 실제 변경, 확보한 증거, 미실행 검증, 미완료 하위 작업.

모든 항목을 의무 템플릿으로 만들지 않는다. 작은 동작 하나를 UI·locale별로 기계 분할하지 말고 한 담당자가 완결하며, 독립 동작만 나눈다.

같은 CL이어도 기존 승인 범위와 마일스톤별 검증·receipt를 유지하며, 이미 승인된 마일스톤을 자동 병합하거나 receipt를 공유하지 않는다. 새 계획에서는 목표와 검증이 결합된 소작업을 하나의 마일스톤으로 묶을 수 있지만, 1시간 상한·승인 범위·명확한 완료 조건을 지킨다. medium 구현자가 하위 작업을 나누면 주담당이 전체 파일 소유, 하위 반환, 잔여 작업을 모아 코디네이터에게 보고한다.

## 계획

```json
{
  "grade": "pytest-pass",
  "inputs": ["src", "tests", "pyproject.toml"],
  "environment": {"python": "3.12", "target": "local-test", "revision": "검증 기준 리비전"},
  "commands": [
    {"argv": ["python", "-m", "pytest", "tests/test_feature.py", "-q"], "cwd": ".", "timeoutSeconds": 600}
  ],
  "results": []
}
```

- `inputs`: 동작에 영향을 주는 소스·테스트·데이터·설정·도구의 실제 상대 경로. 폴더는 하위 파일과 새 파일·삭제를 함께 감지한다.
  생성 로그·미션 상태 폴더·빌드 출력은 넣지 않는다. 프로젝트 밖 입력은 거부한다.
- `environment`: 실제 대상·런타임·리비전 식별자. 대상 DB·서버·도구 버전이 바뀌면 갱신한다.
  외부 상태를 고정할 수 없는 실기·통합 검증은 `--force`로 다시 실행한다. 파일 해시만으로 외부 상태가 같다고 보지 않는다.
- `commands`: 셸 문자열 대신 argv 배열. 명령은 계획 순서로 실행하고 첫 실패에서 끝낸다.
  명령별 제한 시간은 1~3600초다. 별도 백그라운드 자식을 남기는 명령은 넣지 않는다.
  기존 미션 가드가 막는 submit·sync 등은 검증 실행기에서도 거부한다.
- `results`: 실행 명령이 이번 런에 쓴 JSON 결과를 추가 검사한다. 예:

```json
{
  "path": "Unity/Game/Temp/mission-verify.json",
  "equals": {"status": "passed"},
  "positive": ["tests.0.startedCount"],
  "projectField": "projectPath",
  "project": "Unity/Game"
}
```

`editmode-pass`는 프로젝트 경로·passed 상태·양수 실행 수 검사가 필수다.
필터가 여러 런으로 나뉘면 각 런의 실행 수를 모두 positive에 지정한다. 결과를 쓰지 않은 종료 코드 0은 통과가 아니다.
Unity 연결·준비 대기·검증·로그 수집·직접 연 에디터 정리는 어댑터의 한 실행 명령으로 묶는다.
기존 인스턴스는 종료하지 않고 프로젝트 불일치·시간 초과는 실패로 반환한다.
`verify` receipt는 입력 변경을 사후에 감지해 재사용을 무효화할 뿐, 입력 변경을 막는 잠금이 아니다. 같은 단위의 통과 receipt는 최신 입력·계획·환경이 모두 일치할 때만 재사용한다. 외부 상태 변경은 기존 규칙대로 `--force`로 재검증한다.

## 한 단위의 흐름

1. `verify M1 --plan <계획.json>`: 입력·계획·환경·로그·결과가 그대로면 통과 기록 재사용, 아니면 실제 실행.
   실패는 종료 코드 1과 로그·기록 경로를 반환한다. 상태를 알아내려고 같은 검증을 재요청하지 않는다.
2. 독립 리뷰: 첫 라운드는 단위 전체. 후속은 `review-scope M1 --plan <계획.json>`의 변경 목록,
   직전 finding, 그 수정이 영향을 주는 계약과 호출자를 본다. clean 근거는 실제 파일로 받는다.
3. `review M1 --receipt <검증.json> --evidence <리뷰.md> --reviewer <독립 에이전트> --kind unit --status clean`.
   finding이 남으면 `--status findings`로 기록한다. 구현자를 독립 리뷰어라고 기록하지 않는다.
4. 완료 조건 확인·체크포인트 후 `complete M1 --receipt <검증.json> --review <리뷰.json> --done-evidence <완료 조건 확인 근거>`.
   최신 검증 기록과 최신 clean 리뷰 근거가 유효할 때만 ledger·done을 쓰고 현재 상태와 다음 단위를 함께 반환한다.
   이후 리뷰가 있거나 최신 리뷰 포인터가 없으면 이전 clean 리뷰로 완료할 수 없다.
   답이 필요한 `human` 조건은 확인 C에 남긴다. CLI는 사람의 승인·의미 판정을 대신하지 않는다.

기록과 로그는 런마다 별도 파일로 남긴다. `*.latest.json`은 다음 실행·범위 조회용 포인터다.
기존 문자열 ledger는 이력으로 계속 읽되 재사용 가능한 기계 검증 기록으로 취급하지 않는다.
원본 이력을 지우지 않고 `context`가 최신 단위·결정과 원본 위치만 반환한다.
