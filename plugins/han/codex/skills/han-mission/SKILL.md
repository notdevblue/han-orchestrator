# 미션 오케스트레이션

작업은 어댑터의 `stages` 순서로 흐른다. 기본은 컨텐츠 확인 → PoC → 구현 → 검토다.
사람 확인은 정해진 지점에서만 받고, 그 사이는 질문 없이 돌고 보고만 한다.

| 확인 | 시점 | 받는 것 |
| --- | --- | --- |
| A | PoC 설계 초안이 나왔을 때 | 설계 스킬의 단계마다 승인(단계가 없는 스킬이면 컨셉·데이터·통신 묶음) |
| B | 구현 계획이 나왔을 때 | (PoC가 있으면) PoC 확인 + 구현 계획 승인 |
| C | 검토가 끝났을 때 | 결과 확인. submit은 이때 사용자가 요청할 때만 |

PoC가 필요 없는 작업이면 A를 건너뛴다. 확인과 멈춤 질문은 파일로 먼저 두고 공유한 뒤 답을 받는다
("사람에게 묻는 법").

나는 코디네이터다. **코드와 프로젝트 파일을 직접 쓰지 않는다.** 미션 폴더의 기록(상태 파일, 작성자가
돌려준 보고서 본문 반영)은 내 몫이다. 브리프를 쓰고, 파견하고,
검증을 파견하고, 상태 파일을 관리하고, 보고한다. 결과를 만든 에이전트가 자기 결과를 판정하지
않게 하려는 분리다. 하위 스킬이 "내가 고친다"고 하는 대목도 `roles.implement` 파견으로 바꿔 읽는다.

## Codex 실행 계약

- `<plugin-root>`는 이 SKILL.md에서 세 단계 위인 플러그인 폴더다. 스크립트 경로는 실제 절대 경로로 바꿔 호출한다.
- `references/codex-roles.md`를 읽고 사용 가능한 서브에이전트 도구로 역할별 생성·결과 수집·후속 지시를 한다.
  등록되지 않은 역할 이름을 도구에 넘기지 않는다. research와 review는 부모 설정을 상속한다.
  implement는 GPT-6.1 Sol / high, implementSmall과 verify는 GPT-6 Luna / high로 고정하며 미등록 파견 세부는 `codex-roles.md`를 따른다.
- 어댑터의 `runtimes.codex` 덮어쓰기를 적용한다. 병합 순서는 adapter → adapter.runtimes.codex → local → local.runtimes.codex다.
- CLI에서 hooks 기능이 켜져 있고 `/hooks`에서 현재 플러그인 훅을 신뢰한 상태여야 한다.
  단독 마커 뒤 ACTIVE와 훅 안내가 모두 확인되기 전에는 미션 파일·프로젝트 파일을 쓰지 않는다.
- 프로젝트의 AGENTS.md와 실제 설치된 Codex 스킬을 우선 확인한다. Claude용 도구 이름·스킬이
  그대로 있다고 가정하지 않는다. 필요한 PoC·리뷰·Unity MCP가 없으면 해당 단계를 미확인으로 보고하고 멈춘다.

## 0. 어댑터 읽기

1. 어댑터를 찾는다. 계약은 `references/adapter-schema.md`의 "어댑터 찾기"이고, 가드 훅과 같은 순서다.
   - 작업 폴더에서 위로 올라가며 `.codex/orchestrator/adapter.json`, 같은 폴더의 `.claude/orchestrator/adapter.json` 순서로 찾는다.
   - 없으면 시작 셸의 `HAN_ADAPTERS_DIR`, 없거나 비어 있으면 `<CODEX_HOME>/config.toml` 또는
     `~/.codex/config.toml`의
     `[shell_environment_policy.set].HAN_ADAPTERS_DIR`을 사용해 `projects.json`의 `roots`를 대조한다.
     둘 다 없으면 저장소에서 직접 실행할 때 `<저장소>/adapters`를 쓴다. 이미 경로가 설정됐지만 잘못됐거나
     레지스트리·roots가 맞지 않으면 그 이유를 확인한다. TOML 폴백은 Python 3.11 이상이 필요하다.
   - 둘 다 없거나 `schema`가 1이 아니면 "어댑터 없음"을 알리고 `$han-codex:han-adapter-init`을 권한 뒤 멈춘다.
     대신 일하지 않는다.
2. `adapter.md`가 가리키는 프로젝트 하네스 문서(규칙·라우터·워크플로)를 읽는다.
3. 진행 중인 미션을 찾는다: `<stateDir>/ACTIVE`, 그리고 `<stateDir>/*/mission.md` 중 `상태: 진행`인 것.
   - 있으면 ACTIVE의 `id`·`session`·`openedAt`을 보여 주고, **다른 창에서 아직 돌고 있지 않은지
     사용자에게 확인받은 뒤에만** 이어서 하거나 닫는다. 살아 있는 다른 세션의 미션을 가로채지 않는다.
   - ACTIVE 주인 세션이 남긴 마지막 활동(ACTIVE mtime·미션 폴더 파일)이 `mission.staleHours`(기본 24시간)보다
     오래면 `끊김 의심`으로 표시된다(`active`·`status`·슬롯 status·대시보드). 끊김 의심이어도 자동으로 닫지 않는다.
     사용자가 닫자고 하면 `close-stale --force-close-stale`로 닫는다(ACTIVE 삭제, `상태: 중단`, `force-close.log`).
   - `mission.md`는 `진행`인데 ACTIVE가 없거나 id가 다르면 끊긴 미션이다. 이어서 할지 `중단`으로
     정리할지 사용자에게 묻는다.
   - 사용자가 새 작업을 원하면 먼저 기존 미션을 닫을지 중단할지 묻는다.

## 1. 미션 열기

0. **진입 티어를 먼저 정한다.** S(한두 파일·단일 수정) / M(여러 파일·검증 게이트 1개 이상) / L(여러 레이어·PoC·사람 확인).
   S면 미션을 열지 않고 사용자에게 "미션 없이 처리" 또는 한 번 파견을 제안한다. 사용자가 그래도 미션을 원할 때만
   `--force-tier`로 연다. `init`이 `--tier S`를 `--force-tier` 없이 거부하고, `--tier`가 없으면 경고한다.
1. id는 `YYYYMMDD-<짧은-slug>`(영문·숫자·`-`).
2. 셸 도구로 `echo han-mission open <id>`를 **단독으로** 실행한다. 가드 훅이 `ACTIVE`를 쓰고 이 세션에
   가드를 건다. 마커는 다른 명령과 한 호출에 잇지 않는다(이으면 훅이 전체를 거부한다). 셸 `echo` 출력만으로는
   훅 실행을 증명할 수 없다.
   다른 미션이 진행 중이라 거부되면 사용자에게 알리고 멈춘다. 이때는 아무 파일도 만들지 않는다.
3. **가드가 켜졌는지 확인한다.** 훅이 `미션 <id> 가드 켜짐` 안내를 주고, `<stateDir>/ACTIVE`의 `id`가
   이 미션이며 `session`이 현재 Codex 세션 id여야 한다. ACTIVE가 없거나 id·session이 맞지 않거나
   `가드 꺼짐` 안내(어댑터 못 찾음 등)를 받았으면
   미션을 시작하지 말고 멈춰서 사용자에게 알린다. 가드 없이 미션을 돌리지 않는다.
4. 확인되면 상태 CLI로 `init --tier <M|L> --goal "<목표>"`를 실행한다. ACTIVE가 이 미션이 아니면 CLI가 거부한다.
   `<stateDir>/<id>/`에 템플릿을 복사하고 `상태: 진행`·`티어:`와 목표를 적는다. S로 거부되면 `echo han-mission close <id>`로 닫는다.
   목표 첫 줄은 대상과 이루려는 결과를 짧은 한 문장으로 요약한다. 범위·조건·상세는 빈 줄 아래에 보존한다.
   대시보드는 첫 줄을 한 줄로 보여 주며, 펼치면 목표 전체를 보여 준다.

상태 파일마다 쓰는 사람은 코디네이터 하나다. 서브에이전트는 결과를 돌려줄 뿐 상태 파일을 쓰지 않는다.

- `mission.md` — 목표·단계·확인 상태·컨텐츠 확인 요약·명세 위치·지시
- `units.tsv` — 마일스톤 브리프와 상태
- `ledger.tsv` — 검증 판정
- `decisions.tsv` — `[~]` 결정
- `report.md` — 사람이 읽는 결과·남은 판단. 본문은 작성자가 응답으로 돌려주고 내가 반영한다("사람에게 묻는 법")
- `details/<같은 파일명>.md` — 현재 기술 명세와 실행 근거("사람에게 묻는 법"). 질문의 과거 정의·답 원문은 `details/history/<id>.md`와 기존 개정 보관에 유지
- `questions/<id>.json` — 확인·질문과 문항 상태·답 원문의 정본. `question` CLI로만 기록
- `confirm-<A|B|C>.md`·`ask-<n>.md` — 정본에서 자동 생성한 사람용 문서("사람에게 묻는 법")
- `sessions.tsv` — 미션을 맡은 세션과 대화 기록 경로. 가드 훅이 open·resume 때 쓴다

**단계가 바뀌거나 확인 상태가 바뀔 때마다 `mission.md`를 먼저 고친다.** 이어서 하기가 이 값을 믿는다.

`question publish`로 발행한 미션 루트의 `confirm-*.md`·`ask-*.md`와 대응하는 `details/<같은 파일명>.md`는
대시보드에 자동 표시한다. `document share`·`hide` 여부에 영향을 받지 않으며 공유 전에는 `question check`를 통과해야 한다.
질문의 표시와 답·승인은 별개이며, 사람에게 판단을 요청하기 전 작성·독립 검토 절차는 그대로 따른다.
`report.md`와 그 밖의 연결 자료는 검토한 뒤 `document share`에 각 경로를 직접 나열한다.
이 문서들은 수정하면 다시 검토·공유하고, 공유를 거둘 때는 `document hide`를 쓴다.

### 공유 문서는 Wiki에

`<stateDir>`(예: `_My/missions`)은 미션 진행 기록용이다. 다른 세션·작업자가 참고할 문서의 원본은 프로젝트의
버전 관리 대상 `Wiki/`에 둔다. 종료 때까지 미루지 않고 설계 승인·계약 변경이 확정될 때마다 반영한다.

- 승인된 설계·통신 계약, 결정과 이유, 재현·검증 방법, 남은 제약·후속 과제는 `roles.implement`에 맡겨 Wiki에 반영한다.
  단계별 승인에서는 승인된 범위만 반영한다. 미승인·`[~]` 결정과 보류 과제는 그 상태를 명시한다.
- 기존 Wiki의 관련 문서·폴더·색인을 먼저 찾아 갱신한다. 새 문서가 필요하면 기존 분류에 맞추고 관련 색인에서 연결한다.
  Wiki 위치나 분류를 정할 근거가 없으면 임의로 새 체계를 만들지 말고 사용자에게 묻는다.
- 확인·질문과 답변 원문, `details/`의 검토 근거·승인 이력, 브리프, 실행 로그, 상태 TSV는 미션 폴더에 둔다.
  이미 `_My`에만 있는 공유 내용은 Wiki로 옮긴다. 확인·상세 파일에는 승인 당시 기록과 현재 명세의 Wiki 경로를 남기고,
  현재 명세는 Wiki에서 갱신한다. 상세에만 있던 미승인 설계를 승인된 명세로 옮기지 않는다.
- Wiki 문서는 저장소 안 상대 링크로 연결하고, `_My`·슬롯 절대 경로·개인 대화 기록 없이 이해하고 재현할 수 있게 쓴다.
  필요한 재현 자료는 프로젝트 규칙에 맞춰 함께 보존하고, 검증 결과와 미확인 범위를 구분한다.
- `mission.md`의 `명세`와 `details/report.md`의 `Wiki 인계`에 Wiki 경로와 관련 CL·브랜치, shelve·커밋·제출 상태를 남긴다.
  사람용 `report.md`의 `다음 일`에는 인계 가능 상태·남은 일과 상세 링크를 적는다. 문서를 로컬에 쓴 것과
  다른 작업자가 받을 수 있는 상태를 구분한다. submit·push 권한은 별도다.

### 상태 CLI

`units.tsv`·`ledger.tsv`·`decisions.tsv`와 `mission.md` 머리 줄(상태·현재 단계·확인)은 손으로 고치지 않고 이 CLI로만 쓴다.
빈 브리프 칸, 없는 등급, 판정 없는 `done`, 기록 덮어쓰기를 CLI가 거부한다. 거부되면 메시지대로 고치고, 우회해서 파일을 직접
고치지 않는다. 산문 칸(`목표` 아래 본문, `컨텐츠 확인`, `명세`, `지시`)과 보고서·`details/` 상세는 직접 쓴다.
질문 정본과 생성 문서는 `question` CLI로만 쓴다(`references/question-records.md`).

```
python "<plugin-root>/codex/skills/han-mission/scripts/mission_state.py" <명령> [인자]
```

| 명령 | 쓰임 |
| --- | --- |
| `init [--tier S|M|L] [--force-tier] [--goal]` | §1 미션 폴더 만들기(S는 `--force-tier` 없이 거부, 티어 없으면 경고) |
| `mission set [--stage] [--confirm A=승인]… [--state] [--poc <경로>]` | 단계·확인·상태·PoC 진입 파일 바꾸기 |
| `unit add <id> --goal --files --done --verify --timebox --forbid [--human] [--after]` | §4 마일스톤 추가 |
| `unit set <id> [--status] [--unit] [칸]` / `unit list` | §5 진행 상태·브리프. done은 complete만 허용 |
| `ledger record <unit> --status --grade --evidence [--files]` | §5 판정 기록 |
| `decision add --what --chosen --why --affects [--fixes Dn]` | `[~]` 결정, 앞 기록 정정 |
| `status` | 세 줄 요약(마일스톤 수·최근 판정·걸린 것) |
| `context` | 재개용 요약: 현재 단위·최근 판정·최근 결정·승인 원본 위치 |
| `verify <id> --plan <json> [--force]` | 검증 실행·결과 수집, 유효한 같은 입력 결과 재사용 |
| `review-scope <id> --plan <json>` | 직전 리뷰 이후 바뀐 입력 파일 |
| `review <id> --receipt <json> --evidence <파일> --reviewer <이름> --kind poc\|unit\|integration --status clean\|findings` | 독립 리뷰 근거와 검증 입력 상태 연결 |
| `complete <id> --receipt <json> --review <json> --done-evidence <근거>` | 검증·리뷰 유효성 확인 → 판정·done·다음 단위 요약을 한 호출로 처리 |
| `transcripts` | §6 기록 감사용 대화 기록 경로 |
| `active [--hours N]` | ACTIVE id·세션·열린 시각·마지막 활동과 끊김 의심 여부(읽기 전용, ACTIVE 없어도 됨) |
| `close-stale [--force-close-stale] [--hours N] [--keep-state] [--reason]` | 끊김 의심 ACTIVE만 닫음. 플래그 없으면 미리보기(종료 1). 살아 있으면 거부 |
| `question preview --input <초안JSON>` | 정본을 쓰지 않고 검증한 Markdown 출력 |
| `question publish --input <초안JSON> [--expect-revision N] [--editorial]` | 검토한 질문 정본 발행·개정과 Markdown 생성 |
| `question answer <질문.md> --input <답JSON>` | 사용자 원문·문항 상태·승인 대기를 한 번에 기록 |
| `question restore --input <검토JSON> --source <원본MD> --expect-revision N --expect-sha256 <SHA256>` | Markdown에만 남은 과거 답을 같은 개정에 복원. 원문 대조·독립 검토·원본 백업 필수 |
| `question show <질문.md>` / `question render <질문.md>` | 정본 읽기 / 정본으로 생성 문서 복구 |
| `question check` | 미션 전체 질문의 정본 누락·손상·생성본 불일치 검사. 문제 있으면 종료 1 |
| `document share <미션 상대 경로...>` | 보고·추가 자료를 대시보드에 명시적으로 공유 |
| `document hide <미션 상대 경로...>` | 명시적 공유 해제. 자동 표시 질문·대응 상세는 계속 표시 |
| `document list` | 자동 표시 질문·대응 상세와 명시적으로 공유 중인 문서 확인 |

### p4 쓰기는 작업 공간 고정 래퍼로

어댑터에 `guard.p4Client.require`가 켜져 있으면 미션 중 p4 쓰기 명령(edit·add·sync·revert·shelve 등)은
전역 `-c <작업 공간>`이 있어야 하고, 그 값이 이 폴더의 작업 공간(슬롯이면 `slots.client` 틀, 메인이면
`slots.mainClient`, 아니면 `.p4config`)과 같아야 한다. 직접 쓰지 말고 래퍼를 쓴다.

```
python "<plugin-root>/codex/skills/han-mission/scripts/p4c.py" edit -c <CL> <파일>      # = p4 -c <이 폴더 작업 공간> edit -c <CL> <파일>
python "<plugin-root>/codex/skills/han-mission/scripts/p4c.py" --which                  # 고정될 작업 공간 이름만
python "<plugin-root>/codex/skills/han-mission/scripts/p4c.py" --dry-run sync -q //...  # 실행할 명령줄만
```

래퍼 호출도 가드가 `p4 -c <작업 공간> ...`로 보고 같은 deny 규칙(submit 금지 등)을 적용한다.

검증 계획·재사용·리뷰 범위 계약은 `../../../skills/mission/references/verification-workflow.md`를 따른다. 새 작업 단위는 이 경로를 사용하고,
기존 문자열 ledger는 이력으로 보존한다. 실제 동작·파일 상태가 바뀐 결과를 재사용하지 않는다.

작업 폴더가 프로젝트 밖이면 `--project <폴더>`, 다른 미션을 보려면 `--mission <id>`를 붙인다.

질문·대응 상세는 발행 뒤 별도 공유 등록 없이 표시한다. 발행·답 기록 뒤와 공유 전에는 `question check`로 확인한다.
보고·추가 자료의 공유 명령은 다음처럼 실행한다.
한 명령에 여러 경로를 나열하면 함께 등록한다.

```
python "<plugin-root>/codex/skills/han-mission/scripts/mission_state.py" document share details/diagram.png
python "<plugin-root>/codex/skills/han-mission/scripts/mission_state.py" document share report.md details/report.md details/result.png
python "<plugin-root>/codex/skills/han-mission/scripts/mission_state.py" document hide report.md details/report.md details/result.png
python "<plugin-root>/codex/skills/han-mission/scripts/mission_state.py" document list
```

경로는 미션 폴더 기준이다. `mission.md`와 상태 TSV는 진행 텔레메트리이므로 공유 대상이 아니다.

## 2. 컨텐츠 확인 (`kind: research`)

- `roles.research` 에이전트를 질문별로 병렬로 띄운다. 읽기만 하고 결론과 근거 위치만 돌려받는다.
- 질문은 좁게 나눈다: 기획·결정 기록, 관련 코드 위치, 비슷한 기존 구현, 데이터·설정, 테스트 수단, 위험.
- 결과는 `mission.md`의 `컨텐츠 확인`에 근거 위치와 함께 줄인다.
- 끝에 **PoC가 필요한지** 판단해 적는다. 새 화면·새 규칙·새 데이터 구조처럼 기획 판단이
  필요한 작업은 필요, 버그 수정·리팩터링처럼 이 작업을 맡은 쪽이 승인한 명세가 이미 있는 작업은 불필요.
  불필요하면 확인 A를 `생략`으로 적고 4로 간다.
  - 다른 작업자가 자기 영역을 위해 만든 결정 기록·더미 서버·목업은 이 작업 구조의 명세가 아니다.
    예: 클라 작업자가 만든 더미 서버의 RPC·응답 모양, 결정 기록의 "결과와 영향"에 적힌 서버 테이블 목록,
    먼저 만들어 둔 Proto(정의 데이터)의 표 나눔·칸 구조.
    게임 규칙의 근거로만 쓰고, 저장·통신 구조는 이 작업(서버 이관이면 서버 작업자)이 PoC로 다시 잡는다.
  - 결정 기록·기획 문서·제안서의 상태가 accepted 이거나 작성자가 사용자 본인이어도, 이 작업에서 사용자가 승인한 설계가 아니다. 같은 컨텐츠의 기존 문서·이미 구현된 동작, 같은 사용자의 다른 컨텐츠 결정도 마찬가지다. 거기서 가져온 규칙도 초안에 출처와 함께 올려 승인받는다.
  - 명세가 있는지 애매하면 생략하지 않는다. PoC를 기본으로 두고 생략 여부를 사용자에게 묻는다.
  - 진행 중에 "구조를 다시 잡아야 한다"는 지시를 받으면 §3 PoC로 돌아간다. 어댑터 `design` 단계의
    `skill`을 쓰고, 설계 문서 작성 스킬로 대신하지 않는다.

## 3. PoC (`kind: design`)

1. **설계 초안** — 단계의 `skill`이 정한 설계 항목의 초안을 만든다. 예: 화면 구성·컨셉,
   Proto·Model 목록과 스키마, 통신 설계. 초안끼리 의존하면 앞 초안이 승인된 뒤 뒤 초안을 쓴다(스킬에 단계가 없어 묶음으로 받을 때만 앞 초안을 전제로 쓰고 전제를 적는다).
   초안 작성도 파견이다(조사는 `roles.research`, 문서 초안은 `roles.implementSmall`, 없으면 `roles.implement`).
   어댑터나 프로젝트 문서가 레퍼런스 구현(자매 프로젝트)을 가리키면 초안 전에 그 구현의 Proto·Model·RPC를
   조사하고, 같은 문제를 이미 푼 구조(비용·재화·기간 한정 재화·보유·이력 같은 공용 축 포함)를 따른다.
   다르게 두는 곳은 이유(이 프로젝트 규칙)를 초안에 적는다.
   설계 스킬이 단계별 승인을 정하면(예: game-poc 의 화면·컨셉 → Proto·Model → 통신) 그 순서대로 단계마다 초안을 만들고 확인 A를 단계마다(`confirm-A1.md`, `confirm-A2.md` …) 받는다. 앞 단계 승인 전에는 뒤 단계 초안을 확인 파일에 넣지 않는다. 묶음으로 한 번에 받는 건 스킬에 단계가 없을 때뿐이다.
   단계 안에서도 **뼈대를 먼저** 받는다. 처음 사람용에는 핵심 표·라우트의 칸 목록(이름·타입·한 줄 뜻)과
   결정할 것을 싣는다. 뼈대에 동의하면 전체 명세(enum 값, 지금 행 → 새 행 대응, 참조만 하는 기존 표, 검증)를
   `details/`에 채우고, 사람용에도 이번 단계에서 승인할 컬럼·제약·계약과 결정에 미치는 영향을 제시해 단계 승인을 받는다.
   뼈대 동의와 전체 단계 승인을 구분한다. 칸 구성이 바뀔 때마다 딸린 절을 전부 다시 쓰지 않으려는 것이다.
2. **사람 확인 A** — 초안을 `confirm-A.md`(단계별이면 `confirm-A<n>.md`)로 공유하고 승인받는다("사람에게 묻는 법").
   고칠 곳이 있으면 같은 id의 JSON 초안을 개정해 다시 발행·공유한다("사람에게 묻는 법").
   승인되면 `mission.md`의 `지시`에 승인 내용과 아래 멈춤 규칙을 적고, 마지막 단계까지 승인되면 확인 A를 `승인`으로 바꾼다(단계별이면 `mission.md` 에 `A1 승인` 처럼 단계마다 적는다).
3. **PoC 제작** — 그 스킬의 제작·분담·확인 규칙대로 진행한다. 그 스킬이 제작 중에 사용자 확인을
   요구하는 지점(설계와 다른 구현, 정의되지 않은 값, 대체 검증)은 멈춤 규칙의 "멈추고 묻는" 경우다.
   묻는 동안 그와 무관한 영역은 계속 만든다. 스킬의 확인 절차를 전부 통과해야 PoC 완료다.
   - 파견 직전에 작업 공간에 있는 그 스킬 파일을 다시 읽고, 분담 절이 정한 단위·순서·병렬 여부를 그대로
     파견 단위로 쓴다. 미션이 단위를 새로 나누지 않는다(예: "데이터 먼저, 화면 나중"으로 묶어 순서대로 돌리기).
     스킬이 "맡기기 전에 오케스트레이터가 할 일"을 두면 그 일도 `roles.implement` 단위 하나로 먼저 파견한다.
   - 브리프에는 확인 파일 경로만 적지 않는다. 스킬이 넘기라고 한 항목(원본 위치·볼 범위, 승인된 스키마,
     통신 계약, 파일 사이 이름 계약, 도구 경로 등)을 브리프 본문에 담는다. 브리프가 빈약하면 단위마다
     같은 조사를 다시 해서 느려진다.
   - 스킬이 정한 시작 수단(뼈대 생성기·공용 모듈)이 있으면 기존 산출물 폴더를 참고 구현으로 지정하지 않는다.
   - 승인 뒤 수정·데이터 변경 후속도 바뀌는 영역마다 새 에이전트에 짧은 브리프로 맡긴다. 끝난 에이전트에 이어 보내지 않는다.
   - PoC 산출물 리뷰는 한 라운드만 돈다. 그 스킬의 확인 절(캡처·리포트)로 판정되는 항목은 리뷰 대상에서 뺀다.
4. 완료된 PoC의 설계 항목이 구현 단계의 명세가 된다. 승인된 설계와 PoC를 Wiki의 기존 구조에 반영하고,
   `mission.md`의 `명세`에 Wiki 위치를 적는다. 구현 브리프도 이 경로를 기준으로 쓴다.
   PoC 진입 파일(예: `index.html`)은 `mission set --poc <작업 공간 기준 경로>`로 머리 필드에도 적는다. 슬롯
   대시보드의 미션 문서 목록에 뜬다. 진입 파일이 바뀌면 다시 적는다.

파견 입력·작업 묶기·재리뷰 비용·측정은 `../../../skills/mission/references/usage-policy.md`를 따른다.

## 4. 구현 계획

마일스톤은 에이전트가 **1시간 안에 끝낼 크기**로 쪼갠다. 지금 모델이 80% 확률로 끝내는 작업
길이가 그 정도다(METR). 더 크게 잡으면 실패가 잦아진다. PoC가 있으면 각 마일스톤의 완료 조건은
PoC 명세와의 일치로 쓴다.

`units.tsv`의 칸이 곧 브리프다. 행은 `unit add`로 넣는다. 빈 칸이 있으면 CLI가 거부하는데, 아직 범위가 안 잡힌 것이니 다시 쪼갠다.

| 칸 | 내용 |
| --- | --- |
| `id` | `M1`, `M2` … |
| `goal` | 한 문장 |
| `files` | 건드릴 파일·폴더 |
| `done` | 셀 수 있는 완료 조건 |
| `verify` | 내가 돌릴 검증 명령(`adapter.md` 기준) |
| `timebox` | 분 단위 상한 |
| `forbid` | 하지 말 것 |
| `human` | 사람만 판정할 항목. 없으면 `-` |
| `after` | 먼저 끝나야 하는 마일스톤. 없으면 `-` |
| `unit` | 작업 단위(CL·브랜치). 정해지기 전엔 `?` |
| `started` | `doing`으로 바꾼 시각 |
| `status` | `todo` / `doing` / `done` / `held` |

같이 할 것:

- **파일 배분**: VCS에서 이미 열려 있는 파일(`adapter.md`의 명령)과 독점 락 파일을 피한다.
  승인된 계약이 고정되고 `M1`이 시범 완료된 뒤에는 `.cs`·`.meta`·생성물 파일 소유와 공유 자원 소유가 겹치지 않는 구현 단위를 병렬 배정할 수 있다. `ready`는 후보일 뿐이므로 실제 파일·공유 자원 충돌과 승인 여부를 확인한다. 파일·생성물·독점 자원 소유가 겹치는 마일스톤은 나누지 말고 한 작업 단위로 묶거나 `after`로 순서를 건다.
- **작업 단위 의존**: 뒤 마일스톤이 앞 마일스톤의 심볼·데이터를 쓰는 한 방향 의존은 `after`로 순서를 걸고
  선행 단위의 `done` 뒤에 시작하고 그 순서대로 하나씩 제출한다. 파견·구현 반환만으로 `after`가 충족되지 않는다. 서로 없이는 빌드·검증을 통과하지 못하는 원형 의존은 같은 작업 단위에 묶는다.
  확인 B 전에 작업 단위마다 앞 단위만 먼저 들어간 상태에서 혼자 제출되는지 본다. 같은 CL이어도 기존 승인 범위와 마일스톤별 검증·receipt를 유지하고, 이미 승인된 여러 마일스톤을 자동 병합하거나 receipt를 공유하지 않는다. 새 계획에서는 목표·검증이 함께 완결되는 작은 작업을 한 마일스톤으로 묶을 수 있으며, 1시간 상한·승인 범위·명확한 완료 조건을 지킨다.
- **사람 확인 분리**: 기계로 판정 못 하는 것(`adapter.md`의 사람 확인 항목)은 `human` 칸으로
  빼서 확인 C에 모은다. 그 마일스톤의 기계 판정에 묶지 않는다.
- **시범 단위**: `M1`은 작고 대표적인 것으로 고른다. 브리프 형식과 검증 명령이 맞는지 여기서 확인한다.

브리프에는 해당 작업에 필요한 파일·CL 소유, 사용자 기능 완료 범위, 검증 반례, 반환 항목을 기존 칸과 추가 주의사항에 적는다. 구체 항목은 `../../../skills/mission/references/verification-workflow.md`를 따른다.

**사람 확인 B** — PoC 결과(있으면), 마일스톤별 목표·완료 조건·검증 범위, 사람 확인 목록·위험·예상 규모를
`confirm-B.md`로 공유하고 승인받는다("사람에게 묻는 법"). 정확한 파일·검증 명령·작업 단위는
`details/confirm-B.md`에 보존한다. A를 건너뛴 미션은 여기서 `지시`를 적는다.
확인 B를 `승인`으로 바꾼다. 계획 승인은 submit 승인이 아니다.

## 5. 구현 진행 (`kind: implement`)

`M1`을 먼저 끝까지 완료한다. 이후에는 `after`가 모두 `done`이고 승인된 계약이 고정된 마일스톤 중, 파일과 공유 자원 소유가 겹치지 않는 구현 단위를 병렬로 진행할 수 있다.

에디터는 검증·에셋 임포트가 필요할 때만 쓴다. 조사·계획·서버 작업·리뷰·사람 답 대기 동안 상시 실행하지 않는다.
시작·종료는 코디네이터가 `adapter.md`의 에디터 수명 절차로 맡는다. 구현 에이전트가 Refresh 등이 필요하면 코디네이터에게 요청한다.
이미 열린 해당 프로젝트 에디터는 재사용하고 종료 소유권을 얻지 않는다. 직접 연 것은 PID·시작 시각·프로젝트 경로를 기록한다.
연속된 에디터 작업과 결과 수집이 끝나면 자신이 연 인스턴스만 정상 종료한다. 검증 실패·연결 시간 초과·질문 대기로
빠질 때도 정리하고, 다음 검증 때 다시 연다. 저장 확인·진행 중 작업 때문에 종료되지 않으면 강제 종료하지 않고 보고한다.
세션을 이어받아 소유권을 확인할 수 없는 에디터는 기존 인스턴스로 취급한다.

1. **작업 단위 준비** — `adapter.md` 절차로 CL·브랜치를 만들고 `unit set <id> --status doing --unit <CL>`.
   `after`가 안 끝났으면 CLI가 거부한다. `started`는 CLI가 적는다.
2. **구현 파견** — 승인된 문서·명세가 확정된 소규모 수정은 `roles.implementSmall`(없으면 `roles.implement`),
   설계 판단·여러 계층 변경은 `roles.implement` 하나에게 그 행의 브리프 전부, 관련 명세, `adapter.md`의 관련 절,
   `forbid`를 넘긴다. 구현 에이전트는 실제 변경·증거·미실행 검증·미완료 하위 작업과 자기 확인 결과를 돌려준다. 병렬 파견 조건과 하위 구현을 나눈 주담당의 반환 책임은 `../../../skills/mission/references/verification-workflow.md`를 따른다.
   파견 역할의 부분 반환·실패·턴 상한은 done이나 사용자 승인 요청이 아니다. 코디네이터가 근거와 현재 상태로 원인을 진단하고
   승인 범위 안의 수정과 남은 범위를 새 브리프로 파견한다. 리뷰 3라운드·timebox 상한과 실제 멈춤 조건은 유지한다.
3. **검증 파견** — 브리프의 타깃 명령·입력·환경으로 검증 계획 JSON을 한 번 만들고 `roles.verify` 하나에
   `verify <id> --plan …` 실행과 결과 수집을 맡긴다. 역할이 없으면 `codex-roles.md`의 verify 지시를 쓴다.
   - GPT-6 Luna / high로 고정한다. 모델·추론 수준을 지정할 수 없으면 미확인으로 반환하며 구현 역할로 대신하지 않는다.
   - Unity Refresh·컴파일·EditMode·Play 순서와 입력 동결은 `../../../skills/mission/references/verification-workflow.md`를 따른다.
   - Play 브리프에는 대상 프로젝트·조작 순서·기대 결과·증거 경로를 넣는다. 실패·예상 밖 상태는 증거와 미완료 이유를 메인에 반환한다.
   - 검증자는 코드·테스트·설정·검증 범위·모델을 바꾸거나 하위 에이전트를 띄우지 않는다. 원인 분석·수정·독립 리뷰·완료 판정은 분리한다.
   - 실행기는 명령별 제한 시간 안에서 기다리고 로그·결과 파일·입력 상태를 기록한다. 에이전트가 상태 조회 루프를 만들지 않는다.
   - 같은 계획과 입력·환경·결과가 유효하면 기존 통과 기록을 쓴다. 구현자가 만든 기록도 실행기가 검증하며 메인이 같은 테스트를 반복하지 않는다.
   - 승인된 검증 범위 변경, 결과 손상·환경 변경, 입력 변경이면 다시 실행한다. 입력에는 운영 코드·테스트·데이터·도구와 필요한 설정을 빠뜨리지 않는다.
   - 에디터 준비·검증·결과 수집·정리는 어댑터 실행 명령에 묶는다. 프로젝트 경로·양수 테스트 수·결과 상태를 검사하고 이번에 연 에디터만 정리한다.
4. **마일스톤 리뷰** — fresh `roles.review` 하나로 첫 라운드는 단위 전체를 본다. fork는 쓰지 않는다.
   후속 라운드는 `review-scope`가 가리키는 변경과 직전 finding·영향받는 계약을 본다. 새 파일이나 계약 변경을 범위에서 빼지 않는다.
   고칠 방법이 정해진 finding은 새 구현 에이전트에 짧은 브리프로 넘긴다. 판단이 갈리면 멈춤 규칙을 따른다.
   clean과 findings 모두 실제 결과 파일을 `review`로 기록하고 `--findings-count`(남은 지적 수)와
   `--fixed-count`(이번 리뷰에서 해소를 확인한 직전 지적 수)를 함께 남긴다. 최대 3라운드이며 PoC는 §3의 한 라운드 규칙이 우선한다.
5. **체크포인트와 완료** — 완료 조건을 확인하고 어댑터 절차로 shelve(또는 커밋)한 뒤
   `complete <id> --receipt … --review … --done-evidence …`로 판정·done·다음 단위 조회를 묶는다.
   입력이 바뀌었거나 독립 리뷰 근거가 없으면 CLI가 거부한다. 완료를 위해 상태 TSV를 직접 고치지 않는다.
6. **보고** — 단위 진행은 상태 CLI가 정본이며 완료 응답의 요약을 세션에 보고한다.
   `report.push`가 켜져 있고 알림 도구가 있으면 끝난 단위·등급·새 결정·다음 단위를 짧게 알린다.
   사람에게 확인·질문·종료 결과를 공유할 때만 담당 작성자 하나에게 관련 사람용·상세 문서를 쓰게 한다.
   확인·질문은 작성자의 JSON 초안·상세를 검토한 뒤 `question publish`로 발행하고, 보고서(`report.md`, `details/report.md`)는
   작성자가 응답으로 돌려준 본문을 내가 파일에 반영한다("사람에게 묻는 법"의 1항).
   문서의 원문·답·승인 범위와 독립 공유 전 검토는 유지한다. 마일스톤은 `M2 (정산 라우트 서버 구현)`처럼 뜻을 붙인다.
7. **시범 후 조정** — `M1`에서 브리프 칸이나 검증 명령이 틀렸으면 남은 행을 고친다.
   승인된 목표·범위 안에서만 `unit set`으로 고치고, 고친 내용은 `decision add`로 남긴다.

`complete` 응답에 상태가 포함되므로 뒤에 `status`를 다시 부르지 않는다. 실패·보류 때는 `context`를 본다. `걸린 것`에 timebox 넘김이 뜨면 멈춤 규칙의 마지막 경우다.

"테스트 통과"는 완료가 아니다. `done` 조건 전부와 리뷰 통과가 완료다.

## 6. 검토 & 리뷰 (`kind: review`)

모든 마일스톤이 `done`이나 `held`가 되면 미션 전체를 한 번 더 본다. 마일스톤 리뷰는
조각만 보므로 조각 사이의 어긋남은 여기서 잡는다.

1. **전체 리뷰** — `roles.reviewLoopSkill`이 있으면 그 스킬로 미션의 모든 작업 단위 사이 연결·공유 계약과 아직 검토되지 않은 변경을 범위로 돌린다.
   단위별 clean 근거·검증 기록을 함께 넘기고, 입력이 그대로인 단위를 다시 처음부터 리뷰하지 않는다.
   PoC는 제작 리뷰 1회와 수정 finding의 해소 확인을 하고, 구현용 전체 CL 리뷰 루프를 추가로 붙이지 않는다.
   그 스킬 안에서 "내가 고친다"는 `roles.implement` 파견으로, "사용자에게 올리고 멈춘다"는 멈춤
   규칙으로 바꿔 읽는다. 스킬이 없으면 fresh `roles.review`로 3라운드까지 돈다.
2. **명세 대조** — PoC가 있었으면 구현이 승인된 명세(데이터 스키마·통신 계약·규칙)와
   일치하는지 별도 에이전트로 대조한다. 어긋남은 고치거나 `[~]`로 올린다.
3. **판정과 체크포인트 갱신** — 리뷰 수정으로 파일이 바뀐 마일스톤은 다시 검증해 `ledger`를 갱신하고
   다시 shelve(또는 커밋)한다.
4. **기록 감사** — 기록이 실제로 일어난 일과 맞는지 본다. 사람은 확인 C에서 기록만 읽고 판단하기 때문이다.
   - `transcripts`로 이 미션을 맡은 세션들의 대화 기록 경로를 얻는다.
   - fresh `roles.audit`(없으면 `roles.review`) 하나에게 미션 폴더 경로와 대화 기록 경로를 넘긴다. 구현을
     맡은 역할과 다른 모델이면 더 좋다. 대화 기록은 크니 통째로 읽지 말고 검색해서 보라고 적는다. 파일은 고치지 않는다.
   - 받을 것:
     - `decisions.tsv`·`ledger.tsv`의 줄마다 대화 기록에 실제 행동이 있는지, `evidence`가 가리키는 파일·runId가
       실제로 있고 줄이 말하는 내용을 보여 주는지
     - 대화 기록에는 있는데 기록에 없는 갈림길·방향 전환·버린 시도
     - 대화 기록에 증거 없이 "통과"라고 적힌 검증
     - 지금 보면 위험한 선택(너무 이른 결정, 범위 넓히기, 증상만 덮기)과 사람이 대충 읽으면 놓칠 것
   - 틀린 줄과 빠진 결정은 `decision add --fixes Dn`이나 새 줄로 덧붙인다. 원래 줄은 고치거나 지우지 않는다.
   - `details/report.md`의 `기록 감사`에 첫 줄로 `감사: <에이전트·모델>`, 그 아래에 지적을 줄 번호·시점과 함께 적는다.
     지적이 없으면 `없음`, 감사를 못 돌렸으면 이유를 적는다. 사람용 `report.md`의 `남은 확인`에는
     감사의 핵심 영향·남은 위험·미확인 한계를 요약한다. 감사를 못 했다는 사실과 이유도 사람용에 남긴다.

## 7. 사람 확인 C — 마지막 확인

1. 사람용 `report.md`의 `지금`에는 결과, `남은 확인`에는 판단을 바꾸는 영향·미확인 한계, `다음 일`에는 남은 일을 요약한다.
   검증 범위·`human` 항목·`[~]` 결정의 영향·`held` 이유·전체 감사와 재발 방지 제안, 작업 단위·shelve 목록,
   마일스톤별 등급과 검증 근거, 결정·감사 이력은 `details/report.md`에 빠짐없이 보존한다.
   재발 방지 후보와 남은 선택은 `confirm-C.md`에서 묻고, 사람용 보고의 `남은 확인`에는 해당 항목을 링크한다.
   `details/report.md`의 `Wiki 인계`에는 공유 문서 경로·내용·VCS 상태를 적는다. 공유할 설계·결정·검증 방법·남은 과제가 `_My`에만
   남아 있지 않은지, Wiki에서 문서를 찾을 수 있고 미션 폴더 없이 읽을 수 있는지 확인한다.
2. **피드백 정리** — `han-distill` 스킬(`../han-distill/SKILL.md`) 절차를 `transcripts`가 준 대화 기록 전부로 돌려
   사용자 피드백 중 남길 것을 확인 C JSON 초안의 `body`에 `## 피드백 반영 후보`로 싣는다. 반영은 확인 C 답에서 고른 번호만,
   미션 안에서 한다. 남길 게 없으면 그 절에 `없음`이라고 적는다.
3. `confirm-C.md`에 결과와 마지막 결정·확인할 항목을 설명하고 `report.md`를 연결해 공유한 뒤 답을 기다린다("사람에게 묻는 법"). 이 동안 가드는 켜 둔다. 사용자가 고칠 것을 말하면
   그 수정도 미션 안에서 5·6 절차로 한다.
4. **닫기** — 사용자가 확인 C에서 "닫자"나 submit을 요청하면 확인 C에서 확정된 변경을 Wiki와 `details/report.md`의
   `Wiki 인계`에 반영하고, 사람용 `report.md`의 `다음 일`에 인계 가능 상태·남은 일과 상세 링크를 갱신한다.
   닫을 때는 `mission set --state 닫힘`을 실행하고, 그다음 호출에서 `echo han-mission close <id>`를
   단독으로 실행해 가드를 끈다(훅이 `allow-once`도 지운다).
   - "닫자"만 요청하고 submit은 요청하지 않으면 위 순서로 바로 닫는다.
   - submit을 요청하면 미션을 연 채로 제출하고, 제출이 모두 끝난 뒤에 닫는다. 사용자의 요청을 그 범위(요청한 CL들)의
     명시적 승인으로 보고, 가드가 막는 제출 명령은 "막힌 명령의 1회 허용"으로 하나씩 실행한다.
     어댑터가 명시한 읽기 전용 사전 판별은 제출 승인과 별개다. 제출될 CL에 들어갈 Wiki 반영은 제출 전에 끝낸다.
   - 범위 밖 CL을 제출하거나 제출 검사에 실패한 뒤 다시 제출하려면 새 승인이 필요하다. 검사가 실패하면 원인과
     수정안을 보고하고 멈춘다.
   - 요청한 CL이 모두 제출되고 어댑터가 정한 제출 뒤 확인(예: 배포 산출물 재발행)이 끝나면 `details/report.md`의
     `Wiki 인계`와 사람용 `report.md`의 `다음 일`에 제출 결과(제출 번호)를 적은 뒤 닫는다.

## 사람에게 묻는 법

확인 A·B·C와 멈춤 질문은 **검토한 JSON 초안을 발행하고 생성 문서를 공유한 뒤** 현재 미션 대화에서 답을 받는다.
질문·문항 상태·답 원문은 `questions/<id>.json`이 정본이고 루트 `ask-*.md`·`confirm-*.md`는 자동 생성본이다.
생성본과 정본을 직접 고치지 않는다. 작성·개정은 `question publish`, 답 기록은 `question answer`로만 반영한다.
대시보드는 읽기 전용이며 답·승인은 채팅에서 받는다. 기존 `## 사용자 입력`·`.dashboard-answers/`와 과거 답은 원문 그대로 보존한다.
형식·개정·입력 예시는 [질문 정본과 답 기록](references/question-records.md)을 따른다.

**번호 쓰기** — 번호만으로 대상을 부르지 않는다. `A1 (화면·컨셉)`, `M2 (정산 라우트 서버 구현)`,
`D3 (보상 지급 시점)`처럼 뜻을 붙인다. 마일스톤은 `goal`, 확인 A는 설계 스킬의 단계 이름에서 딴다.

1. **문서와 작성자 정하기** — 사람용 출력은 `<stateDir>/<id>/confirm-<A|B|C>.md`(단계별이면 `confirm-A<n>.md`),
   `ask-<n>.md`(n은 1부터)다. 작성자는 `references/templates/question.json`으로 별도 초안을 만들고
   기술 명세·실행 근거는 `details/<사람용과 같은 파일명>.md`에 쓴다. 보고는 `report.md`·`details/report.md`로 쓴다.
   초안 파일을 정본 위치에 쓰지 않는다.
   - 작성자는 주입된 `사람용 문서 자료`의 작성 안내에서 해당 양식과 예시만 읽는다. 주입이 없으면 이 스킬 파일이 있는
     실제 폴더를 기준으로 `references/human-writing.md`를 찾는다. 기존 Markdown 양식은 본문 문체·순서·승인 범위의 참고로 쓴다.
     파견할 때 원문·최신 답과 상태·문서 id·개정·JSON 초안·출력·상세 위치와 공통 규칙·작성 안내·선택한 양식·예시의 실제 경로를 넘긴다.
     작성자가 원문과 예시에 대조해 고친 뒤 반환한다. 수정도 작성 담당에게 맡기며 코디네이터가 사후 윤문하지 않는다.
   - 질문 작성자는 JSON 초안과 상세를 직접 쓴다. 코디네이터가 검토를 마친 초안을 `question publish --input <초안JSON>`으로 발행한다.
     보고서(`report.md`, `details/report.md`)는 하네스가 서브에이전트의 보고서 `.md` 작성을 거부하므로, 작성자가 완성 본문
     (또는 절별 교체 내용)을 돌려주고 코디네이터가 받은 그대로 반영한다. 검사·검토에서 나온 수정은 작성자에게 다시 맡긴다.
   - 상세 양식은 `references/details-template.md`다. 같은 id·개정으로 연결하고, 상세를 루트의 `ask-1-details.md`처럼 두지 않는다.
     상세는 현재 명세·승인 근거·적용 범위로 고쳐 쓰며 과거 변경 일지·폐기 표·옛 근거는 보관 위치로 연결한다. 별도 문항 상태 정본을 만들지 않는다. 미션 전체 확인 상태는 `mission.md`·상태 TSV가 맡는다.
2. **판단할 내용 쓰기** — 반복 개정은 현재 상태로 고쳐 쓴다. 첫 3~5줄에 이번 변경을 쓰고 남은 질문은 권장안·대안·영향과 함께 둔다. 끝난 문항은 작성자가 문서 `body`에 실제 현재 선택·유효 조건을 짧게 쓴다. 다른 절에서 명확하면 별도 요약은 만들지 않는다. 질문 id·번호·선택지의 의미·답·상태·승인 범위는 바꾸지 않는다. 예시는 문체와 순서만 참고하고, 현재 명세·전체 근거는 상세에 둔다.
   - 다른 작업·저장소·화면은 주장에 필요한 실제 상태를 먼저 확인한다. 문서나 accepted 표지만으로 구현 완료·이 작업 승인을
     단정하지 않는다. 확인·추론·미확인을 구분하고 선택에 미치는 영향을 질문 옆에 쓴다. 확인 시점·버전·경로·근거는 상세에 둔다.
   - 이번에 승인할 스키마·통신 계약·규칙은 사람용에도 직접 싣는다. JSON의 `body`에 최신 승인 대상 한 벌을 넣고, 데이터는 테이블별 컬럼·타입·키·제약,
     RPC는 라우트별 요청·응답을 제시한다. 변경점만 보고 승인하게 만들지 않는다. 승인 범위·제외 조건을 함께 적고 상세에만 있는 미제시 설계까지 승인된 것으로 보지 않는다.
   - 전체 화면 대응·Proto·Model·클라 메모리·enum·기존 데이터 대응과 검증은 상세에 보존한다.
     기존 Proto도 Model과 같은 깊이로 적는다. 정확한 파일·명령·CL·shelve·runId·감사 원문은 상세에, 판단을 바꾸는 결과·한계는 사람용에 둔다.
3. **개정과 승인 범위 지키기** — `question show <질문.md>`으로 현재 정본을 읽고 별도 초안을 고친다. 문서 이름에는 `.md`가 필요하다. 본문을 개정할 때
   `revision`을 올리고 `question publish --input <초안JSON> --expect-revision <현재개정>`으로 발행한다. 상세도 같은 개정으로 맞춘다.
   이전 정본은 `questions/history/<id>/<revision>.json`에 보존되고 기존 답 이력과 legacy 원문은 유지한다. 질문 정의·답 원문·날짜·대상 개정·승인 범위는 CLI가 `details/history/<id>.md`로 생성한다. 현재 문서에 과거 버전·원문 답을 누적하지 않는다. 답 기록은 질문 개정을 올리지 않는다.
   - 일반 개정에서 `title`·`body`·`heading`이 바뀐 문항은 `pending` 또는 명시적 `withdrawn`으로 두고, 새 개정에 대한 답은 `question answer`로 받는다.
     `intro`·문서 `body`의 전체 계약이 바뀌었는데 해결된 문항을 유지하려면 `approval.status=pending`과 남은 확인 이유를 적는다.
   - 의미·승인 범위를 유지하는 문체 개정은 `--editorial`을 명시한다. 기존 문서의 개정에만 쓰며 문항 id 집합·상태·답과 `approval`·`answers`는 바꾸지 않는다.
     개정 증가·`--expect-revision` 규칙은 같다. 의미 변경을 문체 개정으로 포장하지 않는다.
   - 문항 id·번호는 유지한다. 기존 승인은 그대로인 범위에 유효하다. 승인 대상이 달라지면 바뀐 결정과 영향만 다시 제시하고
     관련 확인 상태는 상태 CLI로 갱신한다. 답이 끝난 ask에 새 결정을 넣지 않고 다음 번호로 묻는다.
   - `전부 권장안대로`처럼 문서·개정·범위가 명확한 답은 각 결정에 대응시킨다. 다시 입력하게 요구하지 않는다.
     무엇을 승인했는지 불분명한 부분만 확인한다.
4. **공유 전 확인** — 코디네이터가 `question preview --input <초안JSON>`의 출력을 임시 Markdown으로 받는다.
   작성자와 별도 검토자가 이 미리보기·상세를 원문·현재 답·고른 예시와 대조한다.
   공통 검사기 `python "<plugin-root>/skills/mission/scripts/check_human_doc.py" <초안JSON> --source <이전JSON> --archive <미션>/details/history/<id>.md`로
   최신 승인 대상·legacy 원문·답 이력과 보관 개정의 보존을 검사한다. 최초 이관은 `--source <원본MD>`로 원문을 비교한다. `<plugin-root>`는 실제 플러그인 루트로 치환하고 Claude는 `${CLAUDE_PLUGIN_ROOT}`를 쓸 수 있다.
   누적 문서를 처음 정리하면 정본 누락 답·설계를 먼저 복원하고 `question render <질문.md>`로 기존 이력을 생성한다. 정본·보관 개정과 일치하는 이력에 비교 원문 개정이 보존됐을 때만 이전 표를 현재 본문에서 정리한다.
   `--source`가 정본 경로이면 대응 이력을 자동 검증한다. 새 문서는 `--source`·`--archive`를 생략한다. 미리보기 Markdown은 사람 검토용이며 보존 비교에는 JSON 초안을 넣는다.
   작성자는 검토 의견도 원문·현재 답에 대조해 수정한다. 최종 검토 뒤 코디네이터가 발행하고 생성본을 확인한다. 수정이 필요하면 초안으로 돌아간다.
   - 발행 뒤와 공유 직전에 `question check`를 실행한다. 정본 누락·손상·생성본 불일치가 있으면 공유 완료로 알리지 않는다.
     정본 내용이 맞고 생성본만 어긋났으면 `question render <질문.md>`으로 복구한 뒤 다시 검사한다. 질문 내용을 고치려면 초안을 개정한다.
   - 첫 화면의 이번 변경·남은 질문과 선택지/영향·최신 승인 대상 한 벌·승인 범위와 제외 조건, 간결한 현재 결과, 상세·전체 이력 링크를 확인한다. 못 본 렌더링·참조 검증은 확인했다고 쓰지 않는다.
   - 생성된 질문과 대응 상세는 대시보드에 자동 표시한다. 본문·상세가 열리는지 확인한 뒤 채팅 링크·알림을 보낸다.
     자동 표시는 검토 완료나 승인 증거가 아니다. `기록 확인 필요`는 코디네이터가 정본·생성본을 대조해 해결한다.
   - 보고와 그 밖의 연결 자료는 코디네이터가 같은 공통 검사기로 검사한 뒤 상태 CLI의 `document share <문서·자료...>`에 각 경로를
     나열하고 `document list`에서 모두 공유 중인지 확인한다. 작성자 반환이나 자동 검사 통과는 공유 증거가 아니다.
   - 문서를 고쳤으면 재검토한다. 명시적으로 공유하는 문서·자료는 재공유하고 목록에서 다시 확인한다.
     실패·누락은 공유 완료로 알리지 말고 문제를 보고하며, 무관한 일은 계속한다.
   - 상세 링크는 본문 뒤에 읽을 내용이 드러나는 이름으로 붙인다. 로컬 뷰어 안에서는 허용 루트의 상대 링크를 쓴다.
     공유 확인 뒤 채팅에는 목적·결정할 것과 사람용 문서 링크를 짧게 보낸다. Codex 앱에서는 이름 있는 Markdown 링크,
     Windows Terminal에서 필요하면 슬래시와 공백 인코딩을 적용한 날 `file:///` URL을 쓴다.
   - `report.push`가 켜져 있고 알림 도구가 있으면 위 공유 확인 뒤 결정할 것과 사람용 파일을 알린다. 확인·멈춤 질문을 긴 질문 도구에 넣지 않는다.
5. **답 기록** — 코디네이터는 답을 받는 즉시 원문·날짜·대상 개정·문항별 갱신을 하나의 reply JSON에 담아
   `question answer <ask-1.md> --input <답JSON>`을 한 번 실행하고 `question check`로 확인한다.
   부분 답도 바로 보존하고 답하지 않은 문항은 그대로 둔다. 질문·되묻기만 있으면 원문을 보존하되 문항을 해결하거나 승인으로 올리지 않는다.
   - `answered`는 답과 적용 범위, `withdrawn`은 철회 근거를 `answer`에 남긴다. 조건부·별도 승인이 남으면 같은 호출에서
     `approval.status=pending`과 남은 조건을 `approval.reason`에 명시한다. 상태 머리글·미답 문항·전체 이력 링크는 CLI가 생성하고 문서 `body`는 그대로 출력한다. 완료 답은 재출력하지 않는다.
   - 현재 선택·유효 조건이 본문에 없거나 달라졌으면 작성자가 초안의 문서 `body`를 고쳐 검토·문체 개정 절차로 발행한다. `권장안대로`·합동답을 반복하지 않고 실제 선택을 쓴다. 다른 절에 이미 명확하면 별도 `## 현재 결과`는 만들지 않는다.
   - 상세에는 현재 승인 근거·범위·미해결 조건과 생성 이력을 연결한다. 원문과 완료 표시를 상세·머리말·현재 결과에 각각 수동 복사하지 않는다.
     `mission.md`의 확인 상태·지시는 상태 CLI와 산문 칸 규칙대로, `[~]` 결정은 `decision add`로 반영한다.
     문항 완료는 미션 전체 A·B·C 승인이 아니며, 부분 승인을 전체 단계 승인으로 올리지 않는다.
   - 현재 미션에서 승인·선행·파일 소유 조건이 갖춰진 독립 단위를 파견한다. 다음 일을 하겠다는 보고만 남기고 끝내지 않는다.
     미해결 설계와 확인 A·B·C의 실제 게이트는 유지한다.

기존 Markdown 질문은 원문을 보존하고 명시적으로 정본으로 전환한다. 모호한 산문을 자동 승인으로 바꾸지 않는다.
일괄 정리도 `references/human-writing.md`의 원문·답·승인 범위 보존을 따른다. 실행 중인 이전 세션은 이 새 지침을 다시 읽는다.

## 멈춤 규칙

기본은 멈추지 않는다. 판단이 갈리면 되돌리기 쉬운 보수적인 쪽을 고르고,
`decision add`로 `[~]` 한 줄(무엇을, 고른 쪽, 이유, 영향 마일스톤)을 남기고 계속한다.

질문을 쓰기 전에 그 전제가 되는 CL·파일 소유, 기록된 답·승인 범위, 도구 연결·프로세스의 현재 상태를 확인한다.
조회로 풀리는 문제와 승인 범위 안의 복구는 코디네이터가 처리한다. 실제로 미정인 제품 규칙·스키마,
되돌릴 수 없는 행동·외부 작업·승인 한계를 아래 멈춤 조건과 대조하고, 이미 해결된 질문은 다시 묻지 않는다.

멈추고 묻는 경우는 다섯뿐이다.

- 다음 마일스톤이 그 결정에 걸려 있는데 보수적인 쪽이 없을 때
- 되돌릴 수 없는 행동이 필요할 때(submit, 삭제, 외부 전송, 배포, 공유 작업 공간 동기화). 확인 C에서 사용자가 요청한 범위의 submit은 §7의 4항으로 진행한다
- 승인된 설계·목표·범위를 바꿔야 할 때
- 하위 스킬이 그 지점에서 사용자 확인을 요구할 때
- 같은 마일스톤이 리뷰 3라운드나 `timebox`를 넘겨도 끝나지 않을 때

멈출 때는 `ask-<n>.md`로 질문을 공유하고("사람에게 묻는 법"), 그 결정과 무관한 일은 계속 진행한다.
이 규칙은 확인 A나 B에서 사용자가 동의한 지시라서, 미션 진행 중에는 "모호하면 먼저 묻기"
같은 일반 규칙보다 우선한다. 미션이 닫히면 일반 규칙으로 돌아간다.

### 막힌 명령의 1회 허용

가드가 막은 명령을 사용자가 **그 자리에서 명시적으로** 승인하면, 그 명령 문자열 그대로를
`<stateDir>/<id>/allow-once`에 한 줄로 쓰고(파일 편집 도구) 같은 문자열로 실행한다. 훅이 한 번
통과시키고 그 줄을 지운다. 승인 없이 이 파일을 쓰지 않는다. 승인은 그 명령 하나에만 해당한다.
훅은 호출한 명령 전체가 한 줄과 정확히 같을 때(앞뒤 공백만 무시)만 통과시키고, 줄 하나는 한 번만 쓰인다(명령이 실패해도
지워진다). 그래서 명령은 한 줄로 단독 실행하고 `&&`로 잇거나 여러 줄로 쓰지 않으며, 같은 명령을 다시 돌리려면 줄을 새로 쓴다.
확인 C에서 사용자가 submit을 요청한 경우 그 요청이 요청한 CL 범위의 승인이다(§7의 4항).

## 중단

사용자가 "미션 중단"이라고 하면 진행 중인 파견이 돌아오길 기다리고, 끝나지 않은 마일스톤을 `held`로
바꾼 뒤 `report.md`를 마무리하고 `mission set --state 중단`을 실행한 다음 `echo han-mission close <id>`로 닫는다.
작업 단위(CL·브랜치)는 지우지 않고 목록만 보고한다. 기록 감사(§6의 4)는 돌리지 않는다.
`details/report.md`의 `기록 감사`에 `감사 안 함: 중단`을 기록하고, 사람용 `report.md`의 `남은 확인`에는 그 사실과 상세 링크를 남긴다.

## 환류

같은 실수가 두 번 나오면 `details/report.md`의 재발 방지 제안에 올리고, 선택은 `confirm-C.md`에서 묻는다.
사람용 `report.md`의 `다음 일`에는 해당 확인 항목을 짧게 링크한다. 한 미션 안의 반복(리뷰 finding, 정정 줄,
`fail` 판정)이든, 지난 미션 `details/report.md`의 제안에 이미 있던 실수든 같다. 사용자가 직접 준 지적은 한 번만
나와도 후보이고, 이건 §7의 피드백 정리(`han-distill`)가 맡는다. 아래 단계 고르기는 두 쪽에 똑같이 쓴다.

제안마다 막는 수단을 **위에서부터** 따져서, 되는 가장 높은 단계를 고른다. 문서·규칙은 어겨도 아무것도
실패하지 않으니 마지막이다.

1. **구조** — 그 실수가 나올 길을 없앤다. 상태의 주인을 하나로, 일을 하는 길을 하나로, 손으로 맞추는 목록을
   원본 하나로 바꾼다. 에이전트가 따라 할 옛 방식·죽은 코드를 지운다.
2. **타입·스크립트·가드** — 잘못된 상태를 쓸 수 없게 하거나, 쓰면 바로 실패하게 한다. 실패 메시지가 고칠
   곳(파일·함수·명령)을 가리키게 한다. 이미 흔한 패턴이면 새로 늘어날 때만 실패시킨다.
3. **테스트** — 그 동작이 깨지면 실패하고 내부만 바뀌면 통과하는 테스트로 막는다.
4. **문서·규칙** — 판단이 필요해서 기계로 못 막는 것만.

제안 한 줄에 넣을 것: 실수가 난 근거(기록 줄·finding·판정), 고른 단계, 더 높은 단계가 안 되는 이유.
2·3단계라면 그 검사가 실제로 났던 실수에서 실패하는지 확인하는 방법도 적는다. 미션 절차 자체의 실수면
han 플러그인(상태 CLI·가드·스킬)이 대상이고, 이때도 스킬 문장 추가보다 CLI·가드 검사가 먼저다.

반영은 사용자가 고른 것만 한다. 프로젝트 문서·`adapter.md`는 프로젝트 문서 규칙대로 고친다.

## 이어서 하기

컨텍스트 압축이나 재시작 뒤에는 먼저 `context`를 돌린다. 미션·승인·VCS 상태를 확인하고,
진행할 단위의 브리프와 관련 명세·결정·판정만 번호로 찾아 읽는다. 전체 TSV·과거 로그를 다시 싣지 않는다.
승인된 계약·미해결 질문·멈춤 조건은 요약에서 생략됐다고 사라진 것이 아니며 원본을 확인한다.
`question check`로 정본·생성본을 대조하고 `기록 확인 필요`를 해결한다. 이전 세션의 질문·답 기록 절차는 새 지침으로 다시 읽는다.

- 같은 세션에서 압축만 됐고 `<stateDir>/ACTIVE`의 `session`이 그대로면 가드가 이미 이 세션에 걸려 있으니 마커가
  필요 없다. 재시작·`codex resume`·다른 창처럼 세션이 바뀌었으면 §0의 사용자 확인을 거친 뒤
  `echo han-mission resume <id>`로 가드를 이 세션에 다시 건다. 셸 출력만으로 성공을 판단하지 않고, 훅 안내와 ACTIVE의 id·현재 세션 id를 확인한다. 세션이 같은지 알 수 없으면 바뀐 것으로 본다.
  resume 뒤에도 §1의 3처럼 ACTIVE와 안내를 확인한다.
- 승인된 확인은 다시 받지 않는다. 대기 중이던 확인은 다시 보여 준다.
- `doing` 행은 열린 파일과 마지막 `ledger` 판정을 보고 다시 검증부터 한다.

## 여러 미션을 동시에

미션은 작업 공간 하나에 하나다. 동시에 돌리려면 어댑터의 슬롯을 쓴다(`$han-codex:han-slots`). 슬롯 폴더에서 띄운
세션이 그 슬롯의 미션 하나를 맡고, 확인 A·B·C도 슬롯 세션마다 받는다. 계획 단계의 파일 배분은 다른 슬롯이
열어 둔 파일까지 피한다.

## 하지 않는 것

- 코디네이터가 직접 코드·프로젝트 파일 수정
- 사용자가 요청하지 않은 submit·머지·배포(확인 C에서 요청한 범위의 submit은 §7의 4항), 다른 세션의 작업 단위에 열린 파일 수정
- 테스트 통과만으로 `done`
- 상시 에이전트 군집, 사람 없는 밤샘 루프, 중단·종료된 세션의 자동 재개
