# 질문 정본과 답 기록

질문·답을 서로 다른 Markdown 절에 나눠 수동 갱신하면 부분 답과 완료 표시가 어긋날 수 있다.
`questions/<id>.json`에 문항 상태와 사용자 원문을 함께 기록하고, 사람용 Markdown은 이 정본에서 생성한다.
대시보드는 읽기 전용이다. 답·승인은 현재 미션 채팅에서 받고 코디네이터가 CLI로 기록한다.
미션 전체 A·B·C 승인, `mission.md` 머리 줄과 `[~]` 결정은 기존 상태 CLI의 별도 경계를 유지한다.

## 정본과 생성본

- 정본: `<미션>/questions/<id>.json`
- 생성본: `<미션>/<id>.md`. `ask-*`·`confirm-*`만 쓰며 id는 경로 구분자 없는 안전한 파일 이름이다.
- 상세: `<미션>/details/<id>.md`. 현재 기술 명세·승인 근거·적용 범위로 고쳐 쓴다.
- 생성 이력: `<미션>/details/history/<id>.md`. 질문 정의·답 원문·날짜·대상 개정·승인 범위와 최초 이관 원문을 보존한다.
- 이전 개정: `<미션>/questions/history/<id>/<revision>.json`

정본과 생성본을 직접 편집하지 않는다. 작성자는 정본 밖의 draft JSON과 상세를 쓰고 코디네이터가 발행한다.
생성본 상태 머리글·남은 질문·전체 이력 링크는 CLI가 만들고 문서 `body`는 그대로 출력한다. 완료 문항의 답을 현재 문서에 다시 생성하지 않는다. 사람용 Markdown 양식·예시는 작성자가 채울 산문의 문체·순서·승인 범위에만 참고한다.
현재 문서에는 현재 목적·남은 질문과 선택지/영향·최신 승인 대상 한 벌·승인 범위와 제외 조건을 둔다.
끝난 문항의 실제 현재 선택·유효 조건은 작성자가 문서 `body`에 간결히 쓴다. 다른 절에서 명확하면 별도 `## 현재 결과`로 반복하지 않는다. 답 원문·옛 선택지·폐기 표·변경 일지는 생성 이력과 기존 개정 보관으로 연결한다.
예시의 사실·선택지·승인을 새 질문으로 가져오지 않는다.

정본 `schema: 1`의 필드는 다음과 같다.

| 필드 | 값과 의미 |
| --- | --- |
| `id` | `ask-1`, `confirm-A2` 같은 문서 id. `.md` 확장자는 붙이지 않음 |
| `revision` | 양의 정수. 질문·선택지·문체 개정 때 증가하며 답 기록으로는 증가하지 않음 |
| `title` | 사람이 결정할 대상이 드러나는 제목 |
| `intro` | 현재 목적·결정 대상을 짧게 쓴 Markdown |
| `items` | 문항 배열. 각 문항은 `id`, `title`, `body`, `status`, `answer`를 가짐 |
| `body` | 최신 승인 대상의 표·계약 한 벌, 현재 선택·유효 조건과 승인 범위·제외 조건. 과거 버전을 누적하지 않음 |
| `approval` | `status: none\|pending\|complete`, `reason`. `pending`이면 남은 조건을 반드시 적음 |
| `answers` | 사용자 원문·대상 개정·문항 갱신의 누적 이력 |
| `legacy_markdown` | 기존 질문을 전환할 때 보존하는 원문. 선택 필드 |

문항은 하나 이상이어야 하며 정해진 필드 외의 키는 거부한다. 문항의 선택 필드 `heading`은 기존 절 제목을 보존할 때 쓴다.
문항 `id`는 개정 뒤에도 유지한다. `body`에는 배경·권장·대안과 영향을 짧게 쓰고 `status`에 상태를 적는다.
새 미답 문항은 `pending`과 빈 `answer`로 만들며, `answered`·`withdrawn`에는 답·적용 범위 또는 철회 근거가 필요하다.
`approval`은 이 문서에 추가로 남은 승인 여부다. 문항에 답했다고 미션 전체 단계가 승인되지는 않는다.
조건부 승인은 `approval.status: pending`과 `reason`에 남은 조건을 적는다.

## 처음 발행하기

아래 `<mission-cli>`는 미션 스킬의 상태 CLI 호출에 쓰는 `scripts/mission_state.py`의 실제 절대 경로다.
필요하면 기존 CLI와 같이 `--project`·`--mission`으로 프로젝트와 미션을 지정한다.
공통 검사기는 `<plugin-root>/skills/mission/scripts/check_human_doc.py`다. `<plugin-root>`는 실제 플러그인 루트로 치환하며
Claude에서는 `${CLAUDE_PLUGIN_ROOT}`를 쓸 수 있다. Codex도 이 공통 파일을 호출한다.

1. 작성자는 [정상 초안](templates/question.json)을 정본 밖의 `draft.json`으로 복사해 문서 id·제목·문항·본문을 채운다.
   상세에는 본문에 없는 기술 세부·실제 확인한 근거를 쓴다. 기존 문서를 고치면 변환 전 원문·정본·생성 이력과 최신 답·승인 범위를 함께 받는다.
2. 코디네이터가 `question preview`의 출력물을 임시 Markdown으로 받고, 작성자와 별도 검토자가 원문·현재 답·고른 양식·예시에 대조한다.
   공통 검사기에 JSON 초안을 넣어 최신 승인 대상·legacy 원문·답 이력 보존을 검사한다. `--source`에는 이전 정본 JSON을 넣고
   `--archive`에는 검증할 생성 이력을 넣는다. `--source`가 미션의 정본 경로이면 대응 이력도 자동 검증한다.
   이력에 비교 원문 개정이 온전히 보존된 경우에만 이전 표를 현재 본문에서 정리할 수 있다.
   최초 이관이면 `--source`에 원본 Markdown을 넣는다. 새 문서는 `--source`·`--archive`를 생략한다.
3. 작성자가 검토 의견을 반영하면 코디네이터가 발행한다. 생성본·상세의 링크와 렌더링을 확인하고 `question check`를 실행한다.
   통과 뒤 생성된 사람용 문서와 상세를 공유한다. 정형 검사는 의미·문체·승인 범위의 독립 검토를 대신하지 않는다.

아래는 새 문서를 처음 발행하는 예다. 기존 문서 정리는 아래 개정 절차의 원문·이력 비교를 거친다.

```sh
python "<mission-cli>" question preview --input draft.json > preview.md
python "<plugin-root>/skills/mission/scripts/check_human_doc.py" draft.json
python "<mission-cli>" question publish --input draft.json
python "<mission-cli>" question check
```

`preview`는 초안을 검증해 Markdown을 출력하며 미션 정본·생성본을 쓰지 않는다. `preview.md`는 사람의 독립 검토용 임시 파일이다.
자동 보존 검사는 JSON 초안과 이전 JSON 또는 최초 이관 Markdown을 비교한다. 과거 표를 정리할 때 생성 이력이 정본·보관 개정과 정확히 일치하는지도 확인한다.
현재 본문에는 최신 승인 대상의 컬럼·타입·키·제약 또는 요청·응답이 직접 있어야 한다. 이력 보관은 이 표·계약을 변경점만으로 대체할 근거가 아니다.
원문에 스키마 표가 있는데 현재 문서에 하나도 없으면 이력 보관과 무관하게 검사를 통과하지 못한다. 어떤 표가 최신 한 벌인지와 컬럼·조건의 일치는 작성자·별도 검토자가 의미를 대조한다.
발행된 문서를 고쳐야 하면 생성본을 편집하지 말고 초안으로 돌아간다. 자동 표시 자체는 검토·공유·승인 증거가 아니다.

## 답을 받는 즉시 기록하기

아래는 가상 문항 하나에 답한 입력 예시다. 실제 답의 원문·날짜·대상 개정과 적용 범위로 바꾼다.
다른 문항은 `updates`에 넣지 않아 미답 상태를 그대로 유지한다.

```json
{
  "schema": 1,
  "id": "reply-20261026-01",
  "revision": 1,
  "at": "2026-10-26",
  "text": "1번은 권장안대로 해 주세요.",
  "updates": [
    {
      "id": "1",
      "status": "answered",
      "answer": "1번 권장안에 동의. 이 문항의 범위에만 적용."
    }
  ]
}
```

```sh
python "<mission-cli>" question answer ask-1.md --input reply.json
python "<mission-cli>" question check
```

답 입력의 `id`는 문서 id가 아니라 중복 실행을 식별하는 고유 작업 id다. 같은 id·같은 입력의 재시도는 멱등이고,
같은 id에 다른 내용을 넣으면 거부한다. `revision`은 답한 질문의 현재 개정, `at`은 날짜 또는 ISO 시각, `text`는 사용자 원문이다.
원문은 줄이거나 다듬지 않는다. `updates`에는 명확히 결정된 문항만 넣는다. 현재 개정에 없는 문항 id의 답 갱신은 거부한다. 되묻기·의견만 있으면 원문을 보존하고 상태는 올리지 않는다.
조건부·별도 승인이 남으면 같은 입력에 `"approval": {"status": "pending", "reason": "남은 승인 조건"}`을 추가한다.
명확한 전체 답은 문항별로 대응시키고, 무엇을 승인했는지 불명확한 부분만 다시 확인한다.

`question answer` 한 번으로 원문 이력·문항 상태·문서의 추가 승인 상태와 생성본을 함께 갱신한다.
부분 답도 전체 해결까지 미루지 않는다. 상태·답 원문 이력은 이 호출로 보존하며 현재 문서에 완료 답을 재출력하지 않는다.
현재 선택·유효 조건이 본문에 없거나 달라졌으면 작성자가 정본 밖의 초안에서 문서 `body`를 고친 뒤 검토·문체 개정 절차로 발행한다. `권장안대로`나 합동답 원문을 반복하지 않고 실제 선택을 쓴다. 다른 절에 이미 명확하면 별도 요약은 만들지 않는다.
`items`·`answers`·상태·승인 범위는 바꾸지 않고 원문·날짜·대상 개정은 전체 이력에서 확인한다. 상세에는 현재 승인 근거·적용 범위와 생성 이력의 위치를 연결한다. 미션 전체 승인 조건이 충족됐는지는 코디네이터가 별도로 확인한다.

## 개정과 복구

기존 누적 문서를 처음 정리할 때는 원문에만 남은 답·설계를 먼저 아래 복원 절차로 정본에 반영한다.
정본이 맞으면 `question render`로 기존 개정의 생성 이력부터 만든 뒤, 현재 상태로 고친 초안을 이 이력과 대조한다.
질문 id·답·상태·승인 범위가 같으면 아래처럼 문체 개정으로 발행한다. 생성 이력이 없거나 원문 개정이 빠져 있으면 보존 검사부터 해결한다.

```sh
python "<mission-cli>" question show ask-1.md
python "<mission-cli>" question render ask-1.md
python "<plugin-root>/skills/mission/scripts/check_human_doc.py" draft-r2.json --source <미션>/questions/ask-1.json --archive <미션>/details/history/ask-1.md
python "<mission-cli>" question publish --input draft-r2.json --expect-revision 1 --editorial
python "<mission-cli>" question check
```

- `show`·`render`에는 `ask-1.md`처럼 `.md`가 붙은 루트 문서 이름을 준다. `show`는 현재 정본 JSON을 출력한다. 이를 읽고 별도 초안을 작성한다.
- 내용 개정은 입력 `revision`을 현재보다 크게 하고 `--expect-revision`에 현재 값을 준다.
  초안·상세는 현재 상태로 고쳐 검토한 뒤 발행하며 이전 개정은 history에 남긴다. 기존 `answers` 이력은 앞부분 그대로 유지하고 legacy 원문도 보존한다.
  현재 문서에 과거 버전·답 원문을 덧붙이지 않는다. 생성 이력은 CLI가 정본과 보관 개정에서 만들고, 상세의 옛 근거·폐기 표는 기존 보관 위치로 연결한다.
- 일반 개정에서 문항의 `title`·`body`·`heading`을 바꾸면 그 문항은 `pending` 또는 명시적 `withdrawn`으로 둔다.
  바뀐 질문의 답을 이전 승인에서 가져오지 않고 새 개정에서 `question answer`로 기록한다.
- `intro`·문서 `body`의 전체 계약이 바뀌었는데 해결된 문항을 유지하려면 문서 `approval.status`를 `pending`으로 두고
  `reason`에 남은 확인 이유·범위를 적는다. 개별 답을 유지한 것과 바뀐 전체 계약을 승인한 것은 다르다.
- 문체만 바꾸고 의미·승인 범위가 같으면 `question publish --input draft-r2.json --expect-revision 1 --editorial`로 명시한다.
  기존 문서의 개정에만 쓸 수 있고 문항 id 집합·상태·`answer`, 문서 `approval.status`·`answers`는 바꿀 수 없다.
  `approval.reason`은 같은 승인 범위·남은 조건의 현재 설명으로 고칠 수 있다. 원문은 답 이력·개정 보관에 남기며, 조건의 추가·삭제나 승인 변경은 문체 개정이 아니다.
  개정 증가·현재 개정 확인 규칙은 같다. 의미 변경을 `--editorial`로 포장하지 않는다.
- 답 기록은 질문 개정을 올리지 않는다. 답이 끝난 ask에 새 결정을 덧붙이지 않고 다음 ask로 묻는다.
  답을 반영한 뒤 서두·현재 명세·관련 문서의 대기 안내를 확인하고 필요하면 검토한 문체 개정으로 발행한다. 질문 상태와 현재 설명을 함께 맞춘다.
- 현재 정본과 내용이 정확히 같은 입력으로 재발행하면 생성본을 복구할 수 있다. 질문 개정을 복구 명목으로 덮어쓰지 않는다.
- `render`는 현재 정본과 보관 개정에서 현재 문서·생성 이력을 복구한다. 질문 내용이 바뀌면 초안 개정·검토·발행으로 돌아간다.

## Markdown에만 남은 과거 답 복원

기존 JSON이 유효하지만 과거 답·승인·설계가 Markdown에만 수동 반영된 경우에는 `render` 전에 원문을 별도 파일로 저장한다.
현재 질문 정의·개정이 그대로이고 기존 문항의 답 기록만 빠졌으면 실제 답 원문·날짜·대상 개정을 확인해
`question answer <문서.md> --input <reply.json>`으로 사용자 원문과 `updates`를 기록하고 `question check`로 확인한다.
정본에 누락된 문항·설계까지 함께 복구해야 할 때 아래 `restore` 절차를 사용한다.
코디네이터가 저장한 원문과 기존 정본을 대조하고, 작성자와 별도 검토자가 복원 JSON의 문항·설계·답 원문·날짜·대상 개정·승인 범위를 검토한다.
`restore`는 그 검토가 끝난 입력에만 쓰는 명시적 기록 수리다. 산문에서 답을 추론하거나 새 승인으로 기록하지 않는다.

```sh
python "<mission-cli>" question preview --input reviewed-recovery.json > preview.md
python "<mission-cli>" question restore --input reviewed-recovery.json --source saved-original.md --expect-revision 3 --expect-sha256 <현재-JSON-바이트의-SHA256>
python "<mission-cli>" question check
```

- 기존 JSON과 Markdown이 모두 있어야 한다. 입력의 문서 id와 revision은 현재 정본과 같아야 하며, 과거 답의 `revision`·`at`·`text`는 실제 기록대로 유지한다.
  현재 개정으로 날짜나 승인 대상을 다시 붙이지 않는다. JSON 누락·손상의 자동 복구에는 쓰지 않는다.
- `--source`에는 저장한 원본 Markdown을 준다. 실행 시 현재 Markdown과 바이트 단위로 같아야 하며 줄바꿈·BOM 차이도 거부한다.
  `--expect-revision`과 `--expect-sha256`은 현재 JSON 개정과 원본 바이트의 SHA256이다. CLI는 기존 미션 쓰기 잠금 안에서 검사하고 백업 뒤에도 JSON·현재 문서·생성 이력 세 파일의 바이트와 이력의 기존 존재 여부를 다시 대조한다.
- 기존 문항 id는 모두 유지한다. 기존 `answers`는 내용·순서가 정확히 같은 앞부분으로 유지하고 `legacy_markdown`의 존재와 원문도 바꾸지 않는다.
  추가하는 각 답의 원문은 근거 Markdown에 있어야 한다. 이 대조에서만 줄바꿈을 통일하고 앞뒤 공백을 제거한다.
- 추가 이력을 순서대로 적용한 결과가 최종 문항 상태·답·approval과 일치해야 한다. 새 해결 문항, 기존 답의 변경·철회·대기 복귀와 승인 상태 변경에는 대응하는 추가 이력이 필요하다.
  문자열 포함 검사는 사실·날짜·대상·승인 의미의 진위를 판정하지 않으므로 독립 검토가 필요하다. 기존 `publish`·`answer`의 개정·답 보호 규칙은 그대로다.
- `<미션>/questions/history/<id>/recovery/<UTC시각>-<고유id>/`에 `before.json`·`before.md` 원본 바이트와 `input.json` 검토 입력,
  생성될 `after.json`·`after.md`, 생성 이력의 `before-history.md`·`after-history.md`, `receipt.json`을 보존한다. 영수증에는 수리 시각·문서 개정·각 파일 SHA256·기존 이력의 존재 여부(`before_history_existed`)와 `prepared`·`complete`·`rolled_back`·`rollback_failed` 상태가 남는다.
  기존 복구 폴더를 덮어쓰지 않는다. 원본을 온전히 보존하므로 미션의 비공개 자료와 같은 경계로 취급한다.
- 검증·전제 조건 실패 시 JSON·현재 문서·생성 이력을 쓰지 않는다. 저장 도중 실패하면 백업을 유지하고 세 파일 중 이 실행이 쓴 내용만 원본 바이트로 되돌린다. 처음 없던 생성 이력은 이 실행이 쓴 바이트와 같을 때 제거한다.
  외부 변경이나 저장 오류로 롤백하지 못하면 백업 위치와 확인 필요 오류를 보고한다. 프로세스 강제 종료 때에는 `prepared` 영수증과 원본을 대조해 수동 확인한다.
- 성공 뒤 같은 명령의 재시도는 이전 SHA256이 맞지 않아 거부된다. 이미 현재 정본과 같은 입력도 새 복구 없이 거부한다. `question check`로 완료를 확인한다.

## 기록 확인과 기존 문서 전환

`question check`는 미션 전체 질문의 현재 문서·생성 이력을 정본·보관 개정과 대조하고 누락·손상·불일치가 있으면 종료 코드 1을 반환한다.
발행·답 기록 뒤와 질문을 공유하기 전에 반드시 실행한다. 재개할 때도 검사해 남은 기록 문제를 확인한다.
정본 누락·손상·생성본 직접 수정·등록과 표시의 불일치는 대시보드의 `기록 확인 필요`로 따로 노출한다.
이를 미답이나 완료로 추정하지 않으며 코디네이터가 원본을 대조해 복구한다.
대시보드의 미답 수·문서 추가 승인 대기는 `items[].status`·`approval.status`만 사용하고 답 문장·권장안·대안을 해석하지 않는다.

기존 Markdown은 원문·답 날짜·선택지·승인 범위를 보존하고 명시적으로 JSON으로 전환한다.
원문은 `legacy_markdown`에 보존하고 확인 가능한 문항 상태·답만 옮긴다. 모호한 산문을 자동 승인으로 바꾸지 않는다.
기존 `## 사용자 입력`과 `.dashboard-answers/`는 과거 입력·전달 이력으로 그대로 보존한다.

CLI를 부르지 않은 채 채팅에만 남은 답은 디스크 검사만으로 알아낼 수 없다.
코디네이터가 채팅의 답을 즉시 기록하고 검사하는 절차를 지킨다. 실행 중인 이전 세션은 새 스킬 지침을 다시 읽어야 한다.

## 도구 실행과 응답 종료 시 검사

Claude·Codex의 `PreToolUse` 가드는 질문 정본·생성본에 대한 직접 파일 쓰기를 막는다.
셸에서 계산된 경로나 별도 프로그램을 거친 모든 쓰기를 사전에 판별하지는 못하므로,
지원하는 쓰기·셸 도구의 동기 `PostToolUse`와 `Stop`에서도 기존 질문 검사기로 현재 기록을 대조한다.
`PostToolUse`는 현재 문서·질문 정본·보관 개정·복구 자료·생성 이력의 경로와 내용 해시가 같으면 같은 세션의 성공한 검사 결과를 재사용한다.
캐시는 시스템 임시 폴더에 두고 미션 기록은 바꾸지 않는다. 입력을 읽지 못하거나 캐시를 사용할 수 없으면 전체 검사로 돌아간다.
실패한 검사와 검사 도중 바뀐 입력은 캐시하지 않는다. `Stop`은 캐시와 관계없이 항상 전체를 검사한다.
사후 훅은 이미 실행된 도구의 변경을 되돌리지 않는다. 불일치가 남으면 경로와 복구 안내를 반환하고 응답 완료를 막으며,
반복된 `Stop`에서도 복구 전까지 같은 검사를 유지한다.

검사는 어댑터의 `stateDir/ACTIVE`에 유효한 미션 id·소유 세션이 있고 훅의 `session_id`와 일치할 때만 적용한다.
같은 부모 세션을 공유하는 하위 에이전트도 검사하며, 다른 세션·보관된 미션·ACTIVE 없는 프로젝트는 막지 않는다.
소유 문맥을 확인할 수 없으면 정상이라고 표시하지 않고 `검사 미실행`을 알린다. 훅은 ACTIVE를 인계하거나 기록·heartbeat를 쓰지 않는다.

유효한 미답 문항과 별도 승인 대기는 검사에 통과한다. JSON 누락·손상과 생성본 불일치만 기록 문제로 다루며,
훅이 질문·답을 자동 생성하거나 산문·대화 기록에서 승인 의미를 추론하지 않는다.
Markdown에만 남은 답은 원문을 보존하고 실제 답·대상 개정을 확인한다. 현재 질문 정의·개정이 같고 답 기록만 빠졌으면
`question answer <문서.md> --input <reply.json>`으로 원문과 `updates`를 기록한다. 누락된 문항·설계까지 복구해야 하면 위 `question restore` 절차를 따른다.
JSON이 맞고 생성본만 잘못됐으면 `question render`, 새 질문 개정이면 `question publish`,
현재 채팅에서 새로 받은 답이면 `question answer`를 사용하고 마지막에 `question check`를 실행한다.
