# 개인 우편을 어떻게 저장하고 받을까요?

<!-- doc-id=confirm-A2 revision=r1 checked=2026-10-20 -->

플레이어마다 받을 우편을 저장하고, 같은 우편을 두 번 받아도 보상이 중복 지급되지 않게 하려는 설계입니다.
이번에는 저장할 값과 우편 받기 요청을 정합니다.

답변 대기 · 2026-10-20 확인

## 결정할 것

### 1. 이미 받은 우편을 다시 요청하면 성공으로 답할까요?

- 권장: 성공으로 답하되 보상은 다시 주지 않습니다. 통신이 끊겨 같은 요청을 보내도 화면에서 받은 상태를 유지할 수 있습니다.
- 대안: 이미 받은 우편이라는 오류로 답합니다. 화면에서 이 오류를 받은 상태로 바꾸는 처리가 필요합니다.

## 승인할 설계

### PlayerMail

| 컬럼 | 타입 | 키 | 제약 | 설명 |
| --- | --- | --- | --- | --- |
| Id | int64 | PK | 0보다 큼 | 우편 번호 |
| PlayerId | int64 | Index | 기존 플레이어 | 받을 플레이어 |
| RewardId | int32 | 없음 | 기존 보상 | 지급할 보상 |
| Received | bool | 없음 | 기본값 false | 보상 수령 여부 |

### ReceiveMail

PlayerId는 로그인 세션에서 정합니다. 우편을 받은 상태로 바꾸는 일과 보상 지급은 함께 저장합니다.

| 요청 필드 | 타입 | 제약·설명 |
| --- | --- | --- |
| MailId | int64 | 로그인 플레이어의 우편 번호 |

| 응답 필드 | 타입 | 제약·설명 |
| --- | --- | --- |
| Result | enum | Success, MailNotFound, RewardUnavailable |
| MailId | int64 | 요청한 우편 번호 |
| Received | bool | 저장된 수령 여부 |

## 범위와 알아 둘 점

우편 목록·읽기는 앞서 승인한 구조를 따릅니다. 위의 권장안을 고르면 이미 받은 우편의 응답은 Success와 Received=true입니다.
없는 우편과 지급할 수 없는 보상은 오류로 답하며, 이때 가방은 바꾸지 않습니다. 실제 서버에서 동시에 요청한 결과는 아직 확인하지 않았습니다.
