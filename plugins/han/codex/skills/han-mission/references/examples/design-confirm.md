개인 독서 목록 앱을 가정해 처음부터 만든 예시다. 이름·설계·답·날짜는 모두 가상이며 실제 프로젝트의 근거나 사용자의 승인이 아니다.
아래는 r2를 고쳐 쓴 r3의 현재 문서다. r1·r2 표·옛 질문·답 원문은 별도 생성 이력에 보존하며 현재 본문에는 최신 설계 한 벌만 둔다.

# 독서 상태를 어떻게 저장하고 바꿀까요?

<!-- doc-id=confirm-A1 revision=3 -->

이번 개정에서는 독서 상태를 바꿀 때 남길 수정 번호를 추가했습니다.
상태 변경 요청은 사용자가 본 수정 번호가 현재 값과 같을 때만 저장합니다.
수정 충돌 때 입력한 상태를 남길지 묻고, 아래 저장 구조·요청·응답 한 벌을 승인받습니다.

답변 대기

## 결정할 것

### 2. 다른 창에서 상태가 바뀌었으면 입력을 남길까요?

- 권장: 저장을 거부하고 입력한 상태를 화면에 남깁니다. 최신 값을 확인한 뒤 다시 선택할 수 있습니다.
- 대안: 입력을 최신 상태로 바꿉니다. 화면은 바로 맞춰지지만 사용자가 방금 고른 상태는 사라집니다.

## 승인할 설계

### BookEntry

| 컬럼 | 타입 | 키 | 제약 | 설명 |
| --- | --- | --- | --- | --- |
| Id | int64 | PK | 0보다 큼 | 책 항목 번호 |
| Title | string | 없음 | 1~200자 | 책 제목 |
| ReadingState | enum | 없음 | Planned, Reading, Finished | 독서 상태 |
| Revision | int32 | 없음 | 1 이상, 수정마다 1 증가 | 수정 번호 |

### ChangeReadingState

수정 번호 비교와 독서 상태 저장은 함께 처리합니다. 수정 번호가 다르면 저장하지 않습니다.

| 요청 필드 | 타입 | 제약·설명 |
| --- | --- | --- |
| EntryId | int64 | 존재하는 책 항목 번호 |
| ExpectedRevision | int32 | 사용자가 본 수정 번호 |
| ReadingState | enum | Planned, Reading, Finished |

| 응답 필드 | 타입 | 제약·설명 |
| --- | --- | --- |
| Result | enum | Success, EntryNotFound, RevisionConflict |
| ReadingState | enum | 현재 저장된 독서 상태 |
| Revision | int32 | 현재 저장된 수정 번호 |

## 승인 범위와 제외 조건

이번 승인은 위 저장 구조·상태 변경 계약과 2번 화면 처리에 적용합니다.
다른 기기 동기화·파일 가져오기·배포는 제외합니다. 동시 요청 동작은 아직 실행해 확인하지 않았습니다.

[현재 명세와 확인 근거](details/confirm-A1.md)

빈 목록으로 시작합니다. 사용자가 직접 추가하는 책에만 적용합니다.
